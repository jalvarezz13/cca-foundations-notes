# 1.1 — Diseñar e implementar bucles agénticos (agentic loops)

> **Dominio 1 — Agentic Architecture & Orchestration · 27% del examen**

---

## 🎯 Concepto clave

Un **agentic loop** es el patrón canónico para que Claude opere como agente: en cada iteración el modelo decide si necesita usar tools, ejecutamos esas tools, devolvemos los resultados al historial, y volvemos a llamar a la API. El loop sale cuando el modelo señala que terminó. **La señal canónica de salida es el campo `stop_reason`, no el texto del asistente.**

```
┌────────────────────┐
│  POST /v1/messages │
└──────────┬─────────┘
           │
           ▼
   ┌────────────────┐       stop_reason == "end_turn" ─────▶ FIN
   │  Respuesta     │
   │  + stop_reason │       stop_reason == "tool_use"  ─────┐
   └────────────────┘                                       │
           ▲                                                ▼
           │                                       ┌────────────────┐
           │                                       │ Ejecutar tools │
           │                                       └───────┬────────┘
           │                                               │
           │     Añadir tool_result al historial           │
           └───────────────────────────────────────────────┘
```

---

## 📚 Profundización

### El ciclo en detalle

1. **Request inicial:** se envía la `messages` array (system + user + historial) y `tools`.
2. **Inspección del `stop_reason`:** Claude responde con un `assistant` message que contiene `stop_reason` y, si corresponde, bloques `tool_use`.
3. **Ejecución de tools:** por cada bloque `tool_use` (puede haber varios) se ejecuta la función real y se prepara un `tool_result` con el mismo `tool_use_id`.
4. **Append al historial:** se añade el `assistant` message tal cual vino + un `user` message con los `tool_result` (los `tool_result` van **primero** dentro del `content`).
5. **Siguiente iteración:** se reenvía toda la conversación. Repetir hasta `stop_reason == "end_turn"`.

### Valores válidos de `stop_reason`

| Valor | Significado | Acción del loop |
|---|---|---|
| `"end_turn"` | El modelo terminó su turno | **Salir del loop** |
| `"tool_use"` | El modelo pidió ejecutar tool(s) | Ejecutar y devolver `tool_result` |
| `"max_tokens"` | Se agotaron tokens de output | Decisión de aplicación (continuar o cortar) |
| `"stop_sequence"` | Coincidió una stop sequence | Salir |
| `"refusal"` | El modelo se negó | Salir o reformular |
| `"pause_turn"` | Pausa de server tools | Reanudar |
| `"model_context_window_exceeded"` | Context window lleno | Compactar y reintentar |

> Los más relevantes para el examen son los dos primeros: **`tool_use` y `end_turn`**.

### Ejemplo mínimo en Python

```python
import anthropic

client = anthropic.Anthropic()

messages = [{"role": "user", "content": "¿Qué tiempo hace en Madrid?"}]

while True:
    response = client.messages.create(
        model="claude-opus-4-5",
        max_tokens=1024,
        tools=tools,
        messages=messages,
    )

    # Apéndice del turno del asistente al historial
    messages.append({"role": "assistant", "content": response.content})

    # Señal canónica de salida
    if response.stop_reason == "end_turn":
        break

    if response.stop_reason == "tool_use":
        # Ejecutar TODAS las tool_use que vinieron en este turno
        tool_results = []
        for block in response.content:
            if block.type == "tool_use":
                result = execute_tool(block.name, block.input)  # tu lógica
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": result,
                })
        # OJO: los tool_result van primero en el content del user message
        messages.append({"role": "user", "content": tool_results})
        continue

    # Otros stop_reasons → decisión de aplicación
    break
```

### Cómo se añaden los `tool_results` al historial

Reglas estrictas que **el examen evalúa**:

- Cada `tool_result` debe llevar el `tool_use_id` que vino en el `tool_use` correspondiente.
- En el `user` message que devuelve resultados, **los `tool_result` van primero** en el array `content`. Si pones texto antes → **400 error**.
- Los `tool_result` deben ir **inmediatamente después** del `assistant` message que tenía los `tool_use`. No insertar nada en medio.
- Si Claude devolvió N bloques `tool_use` en un turno, debes devolver N `tool_result`.
- `tool_result.content` puede ser un string o una lista de bloques (`text`, `image`, `document`).
- Errores de ejecución → `tool_result` con `is_error: true` y el mensaje de error como `content`.

## ⚠️ Anti-patrones

### 🔴 Parsear lenguaje natural para decidir si terminar
```python
# MAL
if "I have completed" in response_text or "Done!" in response_text:
    break
```
El modelo puede decir "Done!" mientras llama a una tool, o no decirlo cuando termina. **Se rompe.**

### 🔴 Topes arbitrarios de iteraciones
```python
# MAL — corta sin razón
for _ in range(5):
    response = client.messages.create(...)
```
Cinco no es un número mágico. Mata tareas legítimas que requieran más pasos. Si necesitas un límite, hazlo por **timeout** o por **coste**, no por iteraciones.

### 🔴 Tratar `tool_use` como excepción
```python
# MAL — asume que tool_use es raro
if response.stop_reason == "tool_use":
    print("Weird, model wants a tool")  # ¡es el flujo NORMAL!
```

### 🔴 Texto antes del `tool_result` en el mismo `user` message
```python
# MAL — devuelve 400
{"role": "user", "content": [
    {"type": "text", "text": "Here is the result:"},   # ← rompe la API
    {"type": "tool_result", "tool_use_id": "...", "content": "..."},
]}
```

### 🔴 Sólo procesar el primer `tool_use` cuando vinieron varios
Si Claude devolvió 3 bloques `tool_use` en el turno, **debes** devolver 3 `tool_result`. Si no, error.

### 🔴 Insertar mensajes entre el `assistant` con `tool_use` y el `user` con `tool_result`
Rompe la secuencia que la API espera. 400.

## ✅ Patrón correcto

```python
def run_agentic_loop(initial_user_message: str, tools: list[dict]) -> str:
    messages = [{"role": "user", "content": initial_user_message}]

    while True:
        response = client.messages.create(
            model="claude-opus-4-5",
            max_tokens=4096,
            tools=tools,
            messages=messages,
        )
        messages.append({"role": "assistant", "content": response.content})

        if response.stop_reason == "end_turn":
            # Extraer respuesta final
            return next(
                (b.text for b in response.content if b.type == "text"),
                "",
            )

        if response.stop_reason == "tool_use":
            tool_results = [
                {
                    "type": "tool_result",
                    "tool_use_id": b.id,
                    "content": execute_tool(b.name, b.input),
                }
                for b in response.content
                if b.type == "tool_use"
            ]
            messages.append({"role": "user", "content": tool_results})
            continue

        # Stops infrecuentes — gestión específica
        if response.stop_reason == "max_tokens":
            raise OutputTooLong()
        if response.stop_reason == "refusal":
            raise ModelRefused()
        if response.stop_reason == "model_context_window_exceeded":
            raise ContextOverflow()
        break
```

**Por qué este patrón es correcto:**

1. **Decisión dirigida por el modelo, no por código de control.** El modelo elige cuándo terminar vía `stop_reason`.
2. Sin tope arbitrario de iteraciones.
3. Procesa **todos** los `tool_use` del turno.
4. Cada `stop_reason` tiene una rama explícita.
5. El historial es la única fuente de verdad: lo añadimos sin transformar lo que devolvió el modelo.

---

## 🔄 Decisión dirigida por el modelo vs árboles preconfigurados

| Aspecto | Árbol preconfigurado (estado finito) | Loop dirigido por modelo |
|---|---|---|
| Quién decide el siguiente paso | Código (switch/case) | Claude vía `tool_use` o `end_turn` |
| Flexibilidad | Baja: cualquier caso nuevo requiere código | Alta: nuevas tools amplían el espacio sin tocar el control |
| Determinismo | Alto | Más bajo (mitigable con hooks/gates) |
| Cuándo usarlo | Workflows fijos, compliance estricto | Tareas abiertas, exploración, recovery |

> En el examen, si la pregunta describe un flujo "abierto" (research, soporte multi-paso, debugging) → **loop dirigido por modelo**. Si es un workflow rígido (KYC, settlement bancario) → **mezcla con hooks/gates** (ver 1.4 y 1.5), pero el loop sigue siendo dirigido por modelo.

## 🧪 Escenario de examen

**Pregunta tipo:** "Un equipo construye un agente que realiza varias búsquedas web y luego sintetiza una respuesta. Notan que a veces termina prematuramente, otras hace búsquedas innecesarias y a veces se queda colgado. ¿Cuál es la causa MÁS probable?"

**Opciones (típicas):**
- A) El modelo es demasiado pequeño.
- B) El código del loop **parsea el texto del asistente** para decidir si terminar o seguir buscando.
- C) Falta usar `tool_choice: "any"`.
- D) Hay demasiadas tools registradas.

**Respuesta:** **B**. Síntomas clásicos de control basado en NL: termina cuando el modelo dice "ya tengo suficiente" (falso positivo de fin), no termina cuando no lo dice, busca de más porque no detecta que ya terminó. La solución es usar `stop_reason == "end_turn"` como señal canónica.
