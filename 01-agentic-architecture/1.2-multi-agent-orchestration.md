> **Dominio 1 — Agentic Architecture & Orchestration · 27% del examen**

---

## 🎯 Concepto clave

En un sistema multi-agente con Claude, la topología canónica es **hub-and-spoke**: un **coordinador** central descompone la tarea, **delega** a varios **subagentes** especializados con contexto aislado, y **agrega** sus resultados. Los subagentes **no se comunican entre sí**: toda comunicación pasa por el coordinador.

```
                ┌──────────────────────────┐
                │      Coordinador         │
                │  (descompone, agrega,    │
                │   selecciona subagentes) │
                └────┬────┬────┬────┬──────┘
                     │    │    │    │
              ┌──────┘    │    │    └──────┐
              ▼           ▼    ▼           ▼
         [Subagent A] [Sub B] [Sub C] [Subagent D]
         (research)   (code)  (review)  (research)
              ⚠️ NO se hablan entre sí ⚠️
```

> La doc oficial usa los términos **coordinator**, **specialization**, **parallelization** y **escalation**. El término literal "hub-and-spoke" es una paráfrasis aceptada de la industria; el patrón es el mismo.

---

## 📚 Profundización

### Rol del coordinador (4 responsabilidades)

1. **Descomposición** — partir la pregunta del usuario en sub-tareas independientes.
2. **Delegación** — escoger qué subagente ataca cada sub-tarea y prepararle el prompt con el contexto necesario.
3. **Agregación** — recibir los outputs de los subagentes y producir la respuesta final coherente al usuario.
4. **Selección dinámica** — si una sub-tarea revela algo nuevo, el coordinador puede spawnear un subagente adicional o iterar.

### Aislamiento de contexto

> **Concepto crítico del examen:** los subagentes **no heredan automáticamente** el historial de conversación del coordinador.

- Cada subagente arranca con su propio system prompt (el de su `AgentDefinition`) y un user message inicial que **el coordinador construye explícitamente**.
- El subagente sólo sabe lo que está en su prompt. Si necesita el ticket original, el coordinador se lo pega.
- Cuando el subagente termina, **solo su resultado final** (el último `assistant` message) sube al coordinador como resultado de la Task tool. El historial interno del subagente se descarta.

**Implicación práctica:** si tienes un caso con muchos hechos relevantes (montos, IDs, fechas), el coordinador debe pasar un **bloque de "case facts"** explícito en el prompt de cada subagente. Si no, alucinarán o pedirán datos.

### Spawn paralelo

El coordinador puede emitir **múltiples bloques `tool_use` de Task** en una **misma respuesta**. La aplicación los ejecuta en paralelo y devuelve los `tool_result` en el siguiente turno.

```python
# En el turno del coordinador, response.content puede tener N tool_use Task
for block in response.content:
    if block.type == "tool_use" and block.name == "Task":
        # Lanzar subagente con la AgentDefinition referida
        spawn_subagent_async(block.input)
```

> Esto es lo que hace que multi-agente sea más rápido que prompt chaining: las sub-tareas independientes se ejecutan **a la vez**, no en serie.

### Cuándo NO usar multi-agente

- Tarea trivial o de un solo paso → overhead innecesario.
- Sub-tareas **muy dependientes** entre sí (cada una necesita la anterior) → mejor un único agente con loop más largo.
- Latencia crítica con sub-tareas baratas → el round-trip extra puede no compensar.

## ⚠️ Anti-patrones

### 🔴 Subagentes que se hablan entre sí

```
Subagent A ──→ Subagent B ──→ Subagent C
```
Rompe el modelo hub-and-spoke. Genera ciclos, pérdida de control y atribución difusa. Si necesitas que B vea lo de A, el **coordinador** pasa el output de A en el prompt de B.

### 🔴 Asumir que el subagente hereda el historial

```python
# MAL — el coordinador no pasa el contexto
coordinator.spawn(agent="legal-reviewer", prompt="¿Es válido?")
# El subagente no sabe QUÉ contrato revisar
```

### 🔴 Descomposición demasiado estrecha

> Si descompones en sub-tareas **demasiado granulares**, cada subagente ve una parte tan pequeña que **no puede detectar issues transversales**.

Ejemplo malo: "Subagente A revisa la línea 1, B la línea 2, C la línea 3…" → ninguno ve el patrón.

Ejemplo correcto: "Subagente A revisa el módulo de auth completo, B revisa pagos completo, C revisa la integración entre ambos."

### 🔴 No iterar tras detectar gap en la síntesis

Si al agregar los resultados el coordinador detecta que falta cobertura, debe **spawnear un subagente adicional** para llenar el gap. Cerrar con la síntesis incompleta es perder calidad.

### 🔴 Subagentes con tools demasiado amplias

Cada subagente debe tener un `allowedTools` mínimo. Si todos tienen todas las tools, pierdes especialización y aumentas misrouting.

## ✅ Patrón correcto

### Coordinator-subagent con paralelización y refinamiento

```python
# 1. Coordinator descompone
coordinator_prompt = """
You are a research coordinator. Decompose the user's question into independent
sub-questions and dispatch them to specialist subagents via the Task tool. Each
subagent gets isolated context, so include all relevant facts in each prompt.

After receiving results, synthesize them. If you detect a gap, spawn additional
subagents to fill it before finalizing.
"""

# 2. AgentDefinitions específicas
agents = {
    "web-researcher": AgentDefinition(
        description="Use for searching public web sources (news, blogs, docs).",
        prompt="You research public web sources. Always cite URLs and dates.",
        tools=["WebSearch", "WebFetch"],
    ),
    "internal-kb": AgentDefinition(
        description="Use for internal company knowledge base queries.",
        prompt="You query our internal KB. Cite document IDs.",
        tools=["kb_search", "kb_get_document"],
    ),
    "financial-data": AgentDefinition(
        description="Use for ticker prices, earnings, financial statements.",
        prompt="You retrieve financial data. Always include source and date.",
        tools=["get_ticker", "get_earnings"],
    ),
}

# 3. El coordinador spawna en paralelo (3 Task tool_use en un mismo turno)
```

### Loop de refinamiento iterativo

```
ITER 1:  Coordinator → [Research A, Research B, Research C] en paralelo
         Agregar resultados → detectar gap: "falta el dato fiscal de 2025"
ITER 2:  Coordinator → [Research D] específico para el gap
         Agregar → cobertura completa → end_turn
```

---

## 🔁 Cuándo iterar y cuándo cerrar

**Iterar** si la síntesis revela:
- Datos que se contradicen entre subagentes (consultar fuente para desempate).
- Áreas que **ningún** subagente cubrió.
- Subagente que reportó fallo de acceso recuperable.

**Cerrar** si:
- Todos los subagentes devolvieron resultados coherentes.
- Los gaps detectados son "no data available" reales (no recuperables).
- Has alcanzado un límite explícito de coste/tiempo (no de iteraciones arbitrarias).

## 🧪 Escenario de examen

**Pregunta tipo:** "Un sistema de research multi-agente produce respuestas incompletas: faltan aspectos importantes de la pregunta. El coordinador divide la pregunta en 8 sub-preguntas muy específicas y las delega en paralelo. ¿Qué es lo MÁS probable?"

**Opciones (típicas):**
- A) Faltan subagentes — añadir más especialistas.
- B) La descomposición es **demasiado estrecha**: cada subagente ve un fragmento tan pequeño que se pierden temas transversales y aspectos no anticipados.
- C) Los subagentes no se comunican entre sí.
- D) El modelo subyacente es demasiado pequeño.

**Respuesta:** **B**. Descomposición excesivamente granular genera cobertura fragmentaria. La solución es subdividir en menos sub-preguntas más amplias **y** añadir un pass de refinamiento donde el coordinador detecte gaps y spawnee subagentes adicionales.

**C** es incorrecto: **NO deben** comunicarse entre sí (rompería hub-and-spoke).
