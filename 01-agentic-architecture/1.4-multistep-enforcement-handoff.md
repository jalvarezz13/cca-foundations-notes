# 1.4 — Workflows multi-paso con enforcement y handoff

> **Dominio 1 — Agentic Architecture & Orchestration · 27% del examen**

---

## 🎯 Concepto clave

Cuando un workflow tiene **reglas de negocio críticas** (verificar identidad antes de un reembolso, no transferir > X sin aprobación, etc.), **no las pongas en el prompt**: ponlas en **hooks / gates programáticos**. El prompt es **guía probabilística**; los hooks son **enforcement determinista**. Cuando el agente no puede resolver, se hace **handoff estructurado** a un humano (o a otro sistema) con todo el contexto necesario.

```
Enforcement determinista (hook):       Guía probabilística (prompt):
┌────────────────────────────┐         ┌─────────────────────────────┐
│ PreToolUse hook            │         │ "Verify identity before      │
│ if tool == "refund":       │         │  issuing refunds, please."   │
│   require(identity_ok)     │         │                              │
└────────────────────────────┘         └─────────────────────────────┘
   100% se cumple                         ~95% se cumple, mata el caso
                                          edge cuando importa
```

---

## 📚 Profundización

### Cuándo se requiere cumplimiento determinista

Usa **hooks o gates** (no prompt) cuando:

1. **Daño irreversible** si la regla falla (transferencias, borrados, despublicaciones, envíos físicos).
2. **Compliance regulatoria** (KYC, GDPR, HIPAA, PCI).
3. **Coste asimétrico** (un falso negativo cuesta mucho más que un falso positivo).
4. **Auditoría obligatoria** — el log del hook es la trazabilidad.

Usa **prompt** cuando:
- Es preferencia de estilo, tono, formato.
- Es heurística sin coste de fallo (sugerir antes de actuar).
- Es guía de selección de tools cuando hay varias razonables.

### Anatomía de un PreToolUse hook (Agent SDK)

```python
async def pre_tool_use_hook(tool_name: str, tool_input: dict, ctx) -> HookResult:
    if tool_name == "issue_refund":
        # 1) Gate de identidad
        if not ctx.session_state.get("identity_verified"):
            return HookResult.block(
                reason="Identity verification required before refund.",
                user_message=(
                    "Antes de procesar el reembolso, necesito verificar tu identidad."
                ),
            )
        # 2) Gate de monto
        amount = tool_input.get("amount_cents", 0)
        if amount > 50_000:  # $500
            return HookResult.escalate(
                reason="Refund amount exceeds policy threshold.",
                handoff_payload={
                    "customer_id": ctx.case_facts["customer_id"],
                    "order_id": ctx.case_facts["order_id"],
                    "amount_cents": amount,
                    "policy": "REFUND_MAX_500",
                    "recommended_action": "manager_review",
                },
            )
    return HookResult.allow()
```

> **Idea clave:** el hook bloquea o transforma la llamada **antes** de que la tool real se ejecute. El modelo no tiene forma de saltarse el hook.

### Decomposición de requests con múltiples concerns

Cuando el usuario plantea **varias preguntas en un solo turno**, el patrón correcto es:

1. **Identificar** los concerns independientes (regla: si la respuesta a uno no depende del otro, son independientes).
2. **Spawnear en paralelo** los subagentes que los atacan.
3. **Agregar** los resultados en una respuesta única que **mantiene el orden** de los concerns del usuario.

Ejemplo: el usuario pregunta:
> "¿Por qué no me llega el envío del pedido X? ¿Y puedo cambiar la dirección del pedido Y? ¿Y devolverme el cobro doble que vi en mi tarjeta?"

→ 3 concerns independientes: `shipment_status(X)`, `address_change(Y)`, `duplicate_charge_refund(...)`. Lanzar 3 subagentes en paralelo.

### Protocolo de handoff estructurado

Cuando el agente no puede resolver y escala (a humano o a otro sistema), **nunca pasar prosa**. Pasar payload estructurado:

```json
{
  "case_id": "CASE-2026-04881",
  "customer_id": "CUST-4892",
  "channel": "chat",
  "category": "refund_request",
  "root_cause": "amount_exceeds_policy",
  "facts": {
    "order_id": "ORD-2024-3349",
    "amount_cents": 78400,
    "policy_threshold_cents": 50000,
    "date_of_purchase": "2024-11-12",
    "identity_verified": true
  },
  "agent_actions_taken": [
    "Verified identity (passport last 4: 8421)",
    "Reviewed order history",
    "Confirmed double-charge"
  ],
  "recommended_action": "approve_refund_with_manager_override",
  "transcript_snippet": "Customer said 'I just want my money back, I've waited 3 weeks'.",
  "sentiment": "frustrated_but_cooperative",
  "sla_remaining_minutes": 22
}
```

> **Por qué importa al examen:** el handoff con campos como `customer_id`, `root_cause`, `amount`, `recommended_action` aparece literalmente en preguntas. Las opciones incorrectas suelen pasar **prosa** o **omitir** campos críticos.

## ⚠️ Anti-patrones

### 🔴 Confiar en el prompt para enforcement crítico
```
system_prompt = "Always verify customer identity before issuing refunds."
```
El modelo lo cumplirá la mayoría de las veces. **Mayoría ≠ siempre.** En 1 de cada 50 casos olvidará verificar. Si la regla es "no se puede reembolsar sin verificar", **debe ser un hook**.

### 🔴 Handoff con prosa
```
"Please help this customer, they are upset about a refund."
```
Pierde IDs, montos, fechas. El humano tendrá que volver a preguntar todo → frustración del cliente, SLA roto.

### 🔴 Procesar concerns secuencialmente cuando son independientes
Tres preguntas independientes en serie → 3x latencia. Lanzarlas en paralelo.

### 🔴 Escalar sin razón estructurada
`"Customer needs human help"` no le dice al supervisor **qué** debe decidir. El campo `root_cause` y `recommended_action` deben estar siempre.

### 🔴 Usar el mismo agente para enforcement y conversación
Si la lógica de enforcement está mezclada con el agente de conversación, cualquier cambio en el prompt puede romper el enforcement. **Separa**: agente conversa, hook gobierna acciones.

## ✅ Patrón correcto

```python
# 1. AgentDefinition con system prompt para tono/estilo (probabilístico)
support_agent = AgentDefinition(
    description="Customer support for refunds, address changes, shipment inquiries.",
    prompt=dedent("""
        You are a customer support agent. Be empathetic and concise.
        Use the tools to look up data; do not invent.
        For refunds above policy, the system will block the action and escalate.
        For refunds, ALWAYS call verify_identity first.
    """),
    tools=["verify_identity", "lookup_order", "issue_refund", "change_address"],
)

# 2. Hooks que enforce reglas críticas (determinista)
async def pre_tool_use(tool_name, tool_input, ctx):
    if tool_name == "issue_refund":
        if not ctx.session_state.get("identity_verified"):
            return HookResult.block(
                reason="identity_not_verified",
                user_message="Necesito verificar tu identidad antes del reembolso.",
            )
        if tool_input["amount_cents"] > 50_000:
            return HookResult.escalate(
                handoff_payload=build_handoff_payload(ctx, tool_input),
            )
    return HookResult.allow()

# 3. Escalado con payload estructurado
def build_handoff_payload(ctx, tool_input):
    return {
        "case_id": ctx.case_id,
        "customer_id": ctx.case_facts["customer_id"],
        "root_cause": "amount_exceeds_policy",
        "facts": {
            "order_id": ctx.case_facts["order_id"],
            "amount_cents": tool_input["amount_cents"],
            "policy_threshold_cents": 50_000,
        },
        "agent_actions_taken": ctx.actions_log,
        "recommended_action": "manager_override_review",
    }
```

## 🧪 Escenario de examen

**Pregunta tipo:** "Un agente de soporte tiene la instrucción 'verifica la identidad antes de procesar reembolsos' en su system prompt. El equipo descubre que en el 2% de casos el agente procesa reembolsos sin verificar. ¿Mejor solución?"

**Opciones:**
- A) Subir la urgencia de la instrucción en el system prompt ("**CRITICAL**: verify identity first.").
- B) Añadir few-shot examples mostrando el orden correcto.
- C) **Convertirlo en un `PreToolUse` hook que bloquea `issue_refund` hasta que `verify_identity` haya devuelto OK** en la sesión.
- D) Cambiar a un modelo más grande.

**Respuesta:** **C**. Para reglas críticas, enforcement determinista (hook) > guía probabilística (prompt). A y B reducen el rate de fallo pero no lo llevan a 0; **C** lo lleva a 0 por construcción.
