# 1.5 — Hooks del Agent SDK: intercepción y normalización

> **Dominio 1 — Agentic Architecture & Orchestration · 27% del examen**

---

## 🎯 Concepto clave

Los **hooks** del Agent SDK son funciones que se disparan **alrededor de cada tool call**. Sirven para dos cosas:

1. **Enforcement determinista**: bloquear o transformar tool calls según reglas de negocio (antes de que la tool real se ejecute) → `PreToolUse`.
2. **Normalización / transformación**: modificar el output de la tool **antes** de que el modelo lo procese → `PostToolUse`.

> **Regla mental:** lo que pongas en un hook es determinista (100%). Lo que pongas en el prompt es probabilístico (~95%).

---

## 📚 Profundización

### `PreToolUse` — antes de ejecutar la tool

Se dispara **antes** de invocar la implementación real. Decide:

- **Permitir** (`allow`) — la tool se ejecuta normal.
- **Bloquear** (`block`) — la tool no se ejecuta. El modelo recibe un `tool_result` con el motivo del bloqueo.
- **Modificar** (`modify`) — reescribe el `tool_input` antes de ejecutar (ej. sanitización).
- **Escalar** (`escalate`) — interrumpe el loop y dispara handoff.

```python
async def pre_tool_use(tool_name: str, tool_input: dict, ctx) -> HookResult:
    # 1) Bloqueo por política
    if tool_name == "issue_refund" and tool_input["amount_cents"] > 50_000:
        return HookResult.block(reason="Refund > $500 requires manager override.")

    # 2) Sanitización del input
    if tool_name == "send_email":
        tool_input["body"] = redact_pii(tool_input["body"])
        return HookResult.modify(new_input=tool_input)

    # 3) Auditoría sin bloquear
    if tool_name.startswith("write_"):
        audit_log.write({"tool": tool_name, "input": tool_input, "ts": now()})

    return HookResult.allow()
```

### `PostToolUse` — después de ejecutar la tool

Se dispara **después** de que la tool devuelva su resultado. Permite:

- **Normalizar formatos** heterogéneos (timestamps, monedas, códigos).
- **Enriquecer** el resultado con metadata derivada.
- **Filtrar** información que no debe llegar al modelo (PII, claves).
- **Convertir** errores opacos en categorías estructuradas.

```python
async def post_tool_use(tool_name: str, tool_result: ToolResult, ctx) -> HookResult:
    if tool_name == "get_orders":
        # Normalizar timestamps a ISO 8601
        for order in tool_result.content:
            if isinstance(order.get("created_at"), int):
                order["created_at"] = unix_to_iso(order["created_at"])
            if isinstance(order.get("created_at"), str) and "Z" not in order["created_at"]:
                order["created_at"] = order["created_at"] + "Z"
        return HookResult.replace(new_result=tool_result)

    if tool_name == "search_kb":
        # Trimear contenido verboso para que no infle el contexto
        for hit in tool_result.content:
            hit["body"] = truncate(hit["body"], max_chars=2000)
        return HookResult.replace(new_result=tool_result)

    return HookResult.passthrough()
```

### Normalizar formatos heterogéneos

> Caso real del examen: tu sistema integra **3 APIs** que devuelven timestamps en formatos distintos: Unix epoch, ISO 8601, formato propietario. Si los pasas al modelo así, alucinará cálculos.

**Solución:** `PostToolUse` que convierte **todos** a un formato canónico (ISO 8601 UTC) antes de inyectar al historial.

| Formato fuente | Ejemplo | Normalizar a |
|---|---|---|
| Unix epoch | `1731408000` | `"2024-11-12T08:00:00Z"` |
| ISO 8601 local | `"2024-11-12 10:00:00"` | `"2024-11-12T08:00:00Z"` |
| Propio | `"12/Nov/2024 10h"` | `"2024-11-12T08:00:00Z"` |
| Códigos numéricos | `status: 3` | `status: "shipped"` |

### Hooks vs instrucciones en prompt — tabla de decisión

| Escenario | Hook | Prompt |
|---|---|---|
| Regla de negocio crítica (monto, identidad) | ✅ | ❌ |
| Normalización determinista de formato | ✅ | ❌ |
| Logging / auditoría | ✅ | ❌ |
| Tono de respuesta | ❌ | ✅ |
| Estilo de salida (verbosidad) | ❌ | ✅ |
| Sugerencia de selección de tool | ❌ | ✅ |
| Bloqueo de PII en outputs | ✅ | ❌ |

## ⚠️ Anti-patrones

### 🔴 Implementar enforcement en el prompt

> "Don't issue refunds above $500."

→ Falla en ~2% de los casos. Si la regla es crítica, ese 2% es un fallo grave.

### 🔴 Hooks que silenciosamente cambian datos sin avisar al modelo

```python
# MAL — silenciosa
tool_result["amount"] = tool_result["amount"] * 100  # cents → dollars
```

El modelo razonará con valores transformados sin saberlo. **Mejor**: documentar en el `tool_result` la transformación o cambiar la **descripción** de la tool para que sea explícito.

### 🔴 Hooks lentos sin async

Un hook síncrono que tarda 2s añade 2s a **cada tool call**. Si hay 10 tool calls, son 20s extra. Usa hooks async o cachea.

### 🔴 Hooks que devuelven errores no estructurados al modelo
```python
return HookResult.block(reason="error")  # Inutil al modelo
```

vs

```python
return HookResult.block(
    reason="amount_exceeds_policy",
    user_message="El monto supera $500. Necesita aprobación de manager.",
)
```

Da al modelo info accionable: puede explicarlo al usuario o pedir más info.

### 🔴 Usar `PostToolUse` para "filtrar" datos sensibles que la tool ya devolvió

Si la tool devuelve PII, ya está en memoria del proceso. **Mejor**: prevenir en la query a la tool (parametrizar selección de campos) o **rediseñar la tool**.

## ✅ Patrón correcto

### Hook combo: enforcement + normalización + auditoría

```python
async def pre_tool_use(tool_name, tool_input, ctx):
    # Enforcement crítico
    if tool_name in DESTRUCTIVE_TOOLS:
        if not ctx.permissions.get(f"allow_{tool_name}"):
            return HookResult.block(reason=f"{tool_name} not allowed in this session.")
    # Sanitización
    if tool_name == "execute_sql":
        if has_destructive_sql(tool_input["query"]):
            return HookResult.block(reason="DDL/DML statements not allowed.")
    # Audit log
    audit_log.append({"phase": "pre", "tool": tool_name, "input": tool_input})
    return HookResult.allow()


async def post_tool_use(tool_name, tool_result, ctx):
    # Normalización de formato
    if tool_name in TIME_RETURNING_TOOLS:
        normalize_timestamps(tool_result)
    # Trim para ahorrar contexto
    if size_kb(tool_result) > 50:
        tool_result = trim_to_relevant_fields(tool_result, schema=ctx.relevant_fields)
    # Audit
    audit_log.append({"phase": "post", "tool": tool_name, "output_size_kb": size_kb(tool_result)})
    return HookResult.replace(new_result=tool_result)


client = ClaudeSDKClient(
    options=ClaudeAgentOptions(
        pre_tool_use_hook=pre_tool_use,
        post_tool_use_hook=post_tool_use,
        ...
    )
)
```

## 🧪 Escenario de examen

**Pregunta tipo:** "Tu agente integra 3 APIs que devuelven timestamps en formatos distintos: Unix epoch, ISO 8601 sin zona horaria, y formato propietario. El agente comete errores aritméticos al calcular días entre eventos. ¿Mejor solución?"

**Opciones:**
- A) Añadir al prompt: "Trata todos los timestamps como UTC y normaliza antes de calcular."
- B) **Implementar un `PostToolUse` hook que normalice todos los timestamps a ISO 8601 UTC antes de inyectar el resultado al historial.**
- C) Usar un modelo más grande para que infiera mejor los formatos.
- D) Pedir a cada API que cambie su formato.

**Respuesta:** **B**. La normalización en hook es determinista (100% se aplica), invisible al modelo (no infla el prompt), y mantiene a las APIs independientes. **A** falla en edge cases. **C** no resuelve el problema de raíz. **D** no es razonable (control externo).
