# 1.6 — Estrategias de descomposición de tareas

> **Dominio 1 — Agentic Architecture & Orchestration · 27% del examen**

---

## 🎯 Concepto clave

Hay dos formas de descomponer una tarea compleja:

1. **Prompt chaining (pipeline secuencial fijo)** — el flujo está cableado en código: paso 1 → paso 2 → paso 3. Útil cuando el camino es conocido y no varía.
2. **Descomposición adaptativa dinámica** — el coordinador descompone **en tiempo de ejecución** según lo que vaya descubriendo. Útil para tareas abiertas (research, exploración, debugging).

**El examen distingue estos casos con precisión.** Saber cuál aplica te ahorra varias preguntas.

---

## 📚 Profundización

### Pipeline secuencial fijo (prompt chaining)

```
   Input ─▶  Step 1  ─▶  Step 2  ─▶  Step 3  ─▶  Output
            (extract)   (validate)   (format)
```

**Cuándo usarlo:**
- Workflow estable: KYC (verificar ID → verificar dirección → verificar fuente de fondos → aprobar).
- Compliance: settlement bancario (validar firma → validar fondos → ejecutar → notificar).
- Generación con etapas claras: outline → draft → review → final.

**Ventajas:** determinista, testeable, optimizable por etapa.
**Desventajas:** rígido. Si aparece un caso nuevo, hay que cambiar código.

### Descomposición adaptativa dinámica

```
                ┌──────────────────────┐
                │  Coordinator         │
                │  (decide en runtime  │
                │   qué descomponer)   │
                └─────────┬────────────┘
                          │
                ┌─────────┼─────────┐
                ▼         ▼         ▼
            [SubA]    [SubB]    [SubC]   ← genera en t=0
                          │
                          ▼
                  Síntesis parcial
                          │
                Detecta gap → spawnea [SubD]  ← genera en t=1
```

**Cuándo usarlo:**
- Research multi-fuente (no sabes a priori qué fuentes son relevantes).
- Code review (el número y tipo de issues a revisar depende del diff).
- Debugging (cada hipótesis abre nuevas líneas de investigación).
- Soporte multi-concern (el usuario plantea N temas).

**Ventajas:** flexible, descubre lo no anticipado.
**Desventajas:** menos determinista, harder to test, riesgo de divergencia si el coordinador no agrega bien.

### Patrón "per-archivo + pass de integración"

> Para **revisión de código**, descomposición canónica del examen.

```
┌────────────────────────────────┐
│  PASS 1 — Per-file review      │   ← descomposición fina
│  (1 subagente por archivo      │
│   editado, en paralelo)        │
└─────────────┬──────────────────┘
              │
              ▼
┌────────────────────────────────┐
│  PASS 2 — Cross-file           │   ← integración
│  integration review            │
│  (1 subagente con visión       │
│   global de los archivos       │
│   modificados y sus            │
│   dependencias)                │
└─────────────┬──────────────────┘
              │
              ▼
       Síntesis final
```

**Por qué funciona:**
- Pass 1 evita **dilución de atención**: cada archivo tiene un revisor dedicado.
- Pass 2 captura **issues transversales** (contratos rotos entre archivos, side-effects).
- Combinados, cubren tanto profundidad como integración.

> **Anti-patrón equivalente:** sólo per-file → pierde integración. Sólo whole-PR → dilución, pierde detalle.

### Planes de investigación adaptativos

Para tareas de exploración (codebase, base de datos, sistema desconocido), el patrón es:

1. **Mapear estructura** — primer subagente: "dame el árbol de directorios + módulos principales".
2. **Identificar áreas de alto impacto** — segundo paso: "de esa estructura, ¿cuál es el core?".
3. **Priorizar** — decidir qué explorar a fondo y qué saltarse.
4. **Ejecutar exploración profunda** — subagentes específicos sobre las áreas priorizadas.
5. **Cerrar** — síntesis con cobertura explícita ("revisado: auth, billing; no revisado por baja relevancia: scripts de migración").

## ⚠️ Anti-patrones

### 🔴 Descomposición demasiado estrecha

Dividir un reporte de research en 20 sub-preguntas hiperespecíficas → cada subagente ve un trozo tan pequeño que se pierden temas transversales. **Coverage incompleta.**

### 🔴 Descomposición demasiado gruesa

Una sola sub-tarea: "Research everything about X" → un solo subagente que se ahoga, mismo problema que no descomponer.

### 🔴 Pipeline fijo cuando se necesita adaptación

Si tu workflow es "review code" y lo modelas como pipeline `lint → security → style`, vas a perder issues que no encajan en ninguna categoría.

### 🔴 Descomposición adaptativa cuando se necesita determinismo

Si la regulación obliga a "verificar identidad antes de fondos antes de aprobar", no dejes que el modelo "decida el orden". Hardcode el pipeline.

### 🔴 No iterar tras detectar gaps

Tras el primer pass, si la síntesis tiene huecos obvios, **spawnear** subagentes adicionales. Cerrar con la síntesis incompleta es perder calidad.

### 🔴 Subagentes que se solapan en cobertura

3 subagentes haciendo la **misma** búsqueda con leve variación → 3x coste, 1x valor. Asegura que cada subagente tiene una **slice única**.

## ✅ Patrón correcto

### Code review con per-file + cross-file

```python
# 1. Identifica archivos modificados
changed_files = ["src/auth.ts", "src/billing.ts", "src/api/handler.ts"]

# 2. Per-file: 1 subagente por archivo, en paralelo
per_file_results = await asyncio.gather(*[
    spawn("code-reviewer", prompt=f"""
        Review the file {f} for bugs, security, and style.
        Output: list of issues with severity (low/med/high) and suggested fix.
    """)
    for f in changed_files
])

# 3. Cross-file integration: 1 subagente con visión global
integration_result = await spawn("integration-reviewer", prompt=f"""
    These files were modified together:
    {changed_files}

    Check for:
    - Broken interfaces between them.
    - Side effects (mutations of shared state).
    - Inconsistent error handling across the call chain.

    Do NOT repeat issues found per-file. Focus on integration.
""")

# 4. Síntesis con dedup
final_report = synthesize(per_file_results, integration_result)
```

### Research adaptativo con refinamiento

```python
# Iter 1 — exploración inicial
initial_subagents = ["web", "internal_kb", "financial_db"]
results_iter1 = await spawn_all_parallel(initial_subagents, base_question)

# Síntesis parcial — detecta gaps
synthesis_v1, gaps = analyze_coverage(results_iter1)

# Iter 2 — sólo para llenar gaps detectados
if gaps:
    gap_results = await spawn_all_parallel(
        [pick_specialist_for(gap) for gap in gaps],
        gap.specific_question,
    )
    final = merge(synthesis_v1, gap_results)
else:
    final = synthesis_v1
```

## 🧪 Escenario de examen

**Pregunta tipo:** "Un sistema revisa pull requests con muchos archivos modificados. El equipo probó dos enfoques: (a) revisar el PR entero con un agente, (b) revisar cada archivo con un subagente. Ambos fallan: (a) pasa por alto detalles, (b) no detecta issues entre archivos. ¿Mejor solución?"

**Opciones:**
- A) Usar (a) con un modelo más grande.
- B) Usar (b) con más subagentes.
- C) **Combinar: un pass per-file en paralelo + un pass de integración cross-file, y sintetizar ambos.**
- D) Pedir al usuario que envíe un PR más pequeño.

**Respuesta:** **C**. Captura profundidad (per-file evita dilución) e integración (cross-file detecta side-effects, contratos rotos). Es el patrón canónico documentado de descomposición para code review.
