# 1.7 — Gestión de sesiones: estado, reanudación y forking

> **Dominio 1 — Agentic Architecture & Orchestration · 27% del examen**

---

## 🎯 Concepto clave

Una **sesión** del Agent SDK / Claude Code agrupa el historial de conversación y el estado asociado. Tres operaciones canónicas:

- **`--continue`** — continúa la **última** sesión del directorio (sin necesidad de ID).
- **`--resume <session-id>`** — reanuda una sesión **específica** por su ID.
- **`--fork-session`** — crea una **rama paralela** a partir del historial actual sin tocar la sesión original.

> El examen distingue resumir vs forkar con precisión: **resume** = continuar la misma línea; **fork** = bifurcar para explorar caminos alternativos.

---

## 📚 Profundización

### `--continue` vs `--resume`

```bash
# Continúa la última sesión en el directorio actual
claude --continue "Y ahora añade tests"

# Reanuda una sesión específica por ID
claude --resume ses_a1b2c3d4 "Sigue desde donde lo dejaste"
```

- `--continue` busca la **más reciente** del proyecto actual y la reanuda.
- `--resume` exige el ID. Útil en CI/CD donde guardas IDs explícitamente.

> En modo headless (`-p`), el JSON output incluye `session_id`. Guárdalo si vas a reanudar más tarde.

```bash
SESSION_ID=$(claude --bare -p "Initial analysis" --output-format json | jq -r '.session_id')
# ...más tarde...
claude --resume "$SESSION_ID" "Continue analysis"
```

### `--fork-session`

Crea una **copia divergente** del historial. La original sigue intacta.

```bash
# Sesión baseline: análisis de arquitectura
claude --resume ses_baseline "Quiero un análisis de arquitectura del módulo billing."

# Fork A: propuesta refactor incremental
claude --resume ses_baseline --fork-session "Detalla un plan refactor incremental."

# Fork B: propuesta rewrite completo
claude --resume ses_baseline --fork-session "Detalla un plan de rewrite completo."

# Ambas ramas comparten el baseline pero divergen sin contaminarse
```

> **`--fork-session` no toca el filesystem.** Sólo hace fork del historial de conversación. Los cambios de archivos van al filesystem real igual.

### `fork_session` programático (SDK)

```python
async with ClaudeSDKClient(options) as client:
    await client.query("Baseline: analiza el módulo billing.")
    # ...recibir respuesta baseline...

    # Fork A
    await client.query(
        "Detalla un plan de refactor incremental.",
        fork_session=True,  # ← clave
    )

    # Fork B (vuelve a forkar desde el baseline original)
    await client.query(
        "Detalla un plan de rewrite completo.",
        fork_session=True,
    )
```

### Informar al agente sobre cambios externos al reanudar

> **Caso típico del examen:** reanudas una sesión donde Claude analizó `src/api.ts`, pero **entretanto** alguien (humano u otro proceso) modificó el archivo. Si reanudas sin avisar, Claude opera con datos obsoletos.

**Solución:**
- Empezar la query reanudada con un **bloque de notas** describiendo cambios externos:
  ```
  Note: Since the last turn, the following files changed externally:
  - src/api.ts (refactored auth middleware)
  - src/billing.ts (new column 'tax_rate')

  Re-read these before continuing.
  ```
- O **reset parcial**: pedirle que vuelva a leer los archivos relevantes antes de seguir.

### Sesión nueva con resumen estructurado vs `--resume`

Dos estrategias para "continuar" trabajo:

| Estrategia | Cuándo |
|---|---|
| `--resume` (mismo historial) | Cambios pequeños o nulos en el contexto externo; quieres continuidad estricta. |
| Nueva sesión + **resumen estructurado** | Pasó mucho tiempo, hay cambios externos significativos, o quieres reset de contexto pero con los hechos. |

El resumen estructurado preserva los **hechos clave** (decisiones tomadas, archivos tocados, restricciones identificadas) sin arrastrar **conversación verbosa**:

```markdown
## Resumen de la sesión previa
- **Objetivo:** refactor del módulo billing para soportar multi-currency.
- **Decisión:** usar `Money` value object en lugar de `(amount, currency)` tuples.
- **Hecho:** introducido `src/value/money.ts`.
- **Pendiente:** migrar `src/billing.ts` y `src/api/checkout.ts`.
- **Restricción:** mantener compatibilidad con el endpoint público v1.
```

> Esto vence al `--resume` cuando el historial original es muy largo (riesgo de "lost in the middle") o cuando los outputs antiguos son obsoletos.

## ⚠️ Anti-patrones

### 🔴 Reanudar sin avisar de cambios externos

El modelo asume que los archivos están como los leyó la última vez. Genera diffs sobre código que ya no existe.

### 🔴 `--continue` cuando hay varias sesiones simultáneas

`--continue` agarra la **más reciente**, no necesariamente la que tú quieres. En equipos con varias sesiones simultáneas, usa `--resume` con ID explícito.

### 🔴 Forkar cuando lo que quieres es retomar

Si quieres seguir con el plan, **no forkees** — `--resume`. Forkar duplica el contexto y luego tienes que decidir cuál de las ramas seguir.

### 🔴 No guardar `session_id` en CI

Cada job de CI corre con sesión nueva → no hay manera de relacionar runs. Si quieres review iterativo en PRs, **guarda el `session_id`** entre runs.

### 🔴 Reanudar una sesión donde los resultados ya están obsoletos

Si la sesión tiene tool_results de hace 2 semanas (búsquedas, fetches), están viejos. Mejor: nueva sesión con resumen + re-fetch.

## ✅ Patrón correcto

### CI/CD que reanuda análisis de un PR tras nuevos commits

```bash
#!/bin/bash
set -euo pipefail

PR_NUMBER="$1"

# Si ya hay session_id guardada para este PR, reanudar
SESSION_FILE=".claude-sessions/pr-$PR_NUMBER.txt"

if [ -f "$SESSION_FILE" ]; then
    SESSION_ID=$(cat "$SESSION_FILE")
    # Informar de cambios externos (nuevos commits) y reanudar
    NEW_COMMITS=$(git log "$LAST_REVIEWED_SHA..HEAD" --oneline)
    claude --resume "$SESSION_ID" --bare -p \
        "Note: New commits since last review:
$NEW_COMMITS

Continue the review, focusing on these new changes. Do NOT repeat previously reported issues."
else
    # Primera review: sesión nueva
    OUTPUT=$(claude --bare -p "Review PR #$PR_NUMBER" --output-format json)
    SESSION_ID=$(echo "$OUTPUT" | jq -r '.session_id')
    echo "$SESSION_ID" > "$SESSION_FILE"
fi
```

### Exploración de alternativas con fork

```python
async with ClaudeSDKClient(options) as client:
    # Baseline compartido
    await client.query(
        "Quiero un análisis del cuello de botella en el endpoint /checkout."
    )
    baseline = await collect(client)

    # Fork A: cache layer
    await client.query("Propón solución con cache layer.", fork_session=True)
    sol_a = await collect(client)

    # Fork B: refactor de query
    await client.query("Propón solución refactorizando la query SQL.", fork_session=True)
    sol_b = await collect(client)

    # Comparar y elegir (el cliente decide, no Claude)
    print(compare(sol_a, sol_b))
```

## 🧪 Escenario de examen

**Pregunta tipo:** "Reanudas una sesión donde Claude analizó tres archivos hace una semana. Mientras tanto, dos de esos archivos fueron refactorizados por un compañero. Reanudas sin más y Claude empieza a hablar de código que ya no existe. ¿Mejor solución para el próximo run?"

**Opciones:**
- A) No reanudar nunca, empezar siempre de cero.
- B) Subir el modelo para que infiera mejor.
- C) **Antes de reanudar, comunicar explícitamente los cambios externos y pedirle que re-lea los archivos afectados antes de continuar.**
- D) Usar `--fork-session` en vez de `--resume`.

**Respuesta:** **C**. Mantiene la continuidad útil de la sesión pero corrige la divergencia entre el estado interno del modelo y el real. **A** descarta contexto valioso; **B** no soluciona el problema; **D** sólo crea una rama, sigue con datos obsoletos.
