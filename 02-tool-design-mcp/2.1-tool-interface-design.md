# 2.1 — Diseño de interfaces de tools con descripciones claras

> **Dominio 2 — Tool Design & MCP Integration · 18% del examen**

---

## 🎯 Concepto clave

La **`description` de una tool es el mecanismo PRIMARIO** que usa Claude para decidir cuándo invocarla. No es el `name`, ni el orden, ni el `system_prompt`: es la **descripción**. Una descripción ambigua o solapada con otra tool produce **misrouting** sistemático. Una descripción específica, con ejemplos y edge cases, hace que la selección sea casi siempre correcta.

---

## 📚 Profundización

### Anatomía de una tool definition

```json
{
  "name": "lookup_order",
  "description": "Look up a customer order by ID. Use this when the user references a specific order number (format: ORD-YYYY-NNNN). Returns order details including line items, status, shipping address, and total. Returns is_error if the order doesn't exist or belongs to a different customer.",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",
        "description": "Order identifier in format ORD-YYYY-NNNN (e.g., ORD-2024-3349)",
        "pattern": "^ORD-\\d{4}-\\d{4}$"
      }
    },
    "required": ["order_id"]
  }
}
```

Tres elementos:
- `name` — corto, snake_case, no genérico.
- `description` — **el cerebro del routing**. Debe incluir:
  - **Qué hace** ("Look up a customer order by ID")
  - **Cuándo usarla** ("when the user references a specific order number")
  - **Formato esperado de input** ("format: ORD-YYYY-NNNN")
  - **Qué devuelve** ("order details, line items, status, shipping address, total")
  - **Cómo se comporta en errores / edge cases** ("is_error if not found or different customer")
- `input_schema` — JSON Schema. Incluye `description` también en cada propiedad.

### Por qué la descripción es el factor dominante

> Anthropic documenta que las descripciones de tools deben ser **muy detalladas** y describir cuándo usar la tool, qué parámetros, los límites y los caveats.

El modelo recibe **toda** la definición de tools en cada turno y elige basándose en la descripción. Si dos tools tienen descripciones similares, el modelo confunde una con otra.

### Misrouting por descripciones ambiguas

🔴 **Ejemplo malo:**
```json
{"name": "analyze_content", "description": "Analyzes content"}
{"name": "analyze_document", "description": "Analyzes a document"}
```
→ El modelo no sabe cuál usar. Misroute ~30-50% de las veces.

🟢 **Ejemplo bueno:**
```json
{
  "name": "analyze_text_sentiment",
  "description": "Returns sentiment score (-1.0 to +1.0) and emotion labels for short plain-text passages (<2000 chars). Use for tweets, reviews, comments. NOT for PDFs or HTML."
}
{
  "name": "analyze_pdf_document",
  "description": "Extracts structured data from PDF documents (invoices, contracts, reports). Returns sections, tables, and key-value fields. Use for files >100KB or with images. NOT for plain text."
}
```

### Impacto del system prompt sobre la selección

Aunque la descripción es primaria, instrucciones **sensibles a keywords** en el system prompt pueden inducir misrouting. Ejemplo:

```
system: "When analyzing content, always be thorough."
```
Si tu tool se llama `analyze_content`, el modelo puede activarla por la coincidencia léxica aunque la situación no lo amerite.

**Solución:** o renombrar la tool, o reescribir el prompt para no mencionar términos que coincidan con nombres de tools.

### Renombrar y dividir tools genéricas

Patrón canónico: si una tool tiene una descripción que abarca múltiples casos, **divídela**:

| Antes (genérica) | Después (específicas) |
|---|---|
| `search` | `search_orders`, `search_customers`, `search_kb` |
| `fetch_url` | `load_document`, `load_image`, `call_partner_api` |
| `process_file` | `extract_pdf_text`, `extract_csv_data`, `convert_image_format` |

Tools específicas:
- Tienen descripciones más concretas → mejor routing.
- Permiten **scoping de permisos** por agente (un subagente sólo recibe `search_kb`).
- Auditoría más fina.

### Plantilla recomendada de descripción

```
[QUÉ HACE en 1 frase]
[CUÁNDO USARLA — disparadores específicos del input del usuario]
[FORMATO DE INPUT esperado, con ejemplo]
[QUÉ DEVUELVE — campos clave]
[QUÉ NO HACE / cuándo NO usarla]
[CÓMO FALLA — qué retorna en errores]
```

### Ejemplos en el `input_schema`

Algunas SDKs soportan `examples` o se simulan con un sub-bloque en `description`:

```json
{
  "type": "string",
  "description": "ISO 8601 date in UTC, e.g. '2024-11-12T08:00:00Z'. Do not pass local time."
}
```

## ⚠️ Anti-patrones

### 🔴 Descripciones genéricas
```json
{"name": "search", "description": "Searches things"}
```
Misrouting garantizado en cuanto haya otra tool con cualquier verbo similar.

### 🔴 Tools solapadas
Dos tools que ambas dicen "analyzes content" se cancelan entre sí.

### 🔴 Tools demasiado generales (poder excesivo)
`fetch_url(url)` permite que el agente alcance **cualquier** URL. Mejor: `load_document(document_id)` que sólo accede a documentos del catálogo interno.

### 🔴 Solo el `name` carga el peso semántico
```json
{"name": "send_invoice_email", "description": "Sends email"}
```
El nombre ayuda pero el modelo no usa el nombre como descripción. Si la descripción es pobre, el routing es pobre.

### 🔴 No documentar errores en la descripción
Si la tool puede fallar con "customer not found", "permission denied", "rate limited", el modelo necesita saberlo en la descripción para razonar sobre la respuesta a fallos.

## ✅ Patrón correcto

### Tool bien descrita para soporte al cliente

```json
{
  "name": "lookup_order_by_id",
  "description": "Retrieves a customer order by its unique ID. Use this tool when the user references a specific order number explicitly (format: ORD-YYYY-NNNN, e.g., ORD-2024-3349). Returns: order status, line items, shipping address, total amount, and refund eligibility. Returns is_error=true with errorCategory='not_found' if the order doesn't exist; with errorCategory='permission' if the order belongs to another customer; with errorCategory='transient' on backend errors. Do NOT use this tool for order searches by date, product, or customer name—use 'search_orders' for that.",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",
        "description": "Order identifier in format ORD-YYYY-NNNN.",
        "pattern": "^ORD-\\d{4}-\\d{4}$",
        "examples": ["ORD-2024-3349", "ORD-2025-0001"]
      }
    },
    "required": ["order_id"],
    "additionalProperties": false
  }
}
```

**Por qué funciona:**
1. `description` cubre QUÉ, CUÁNDO, FORMATO, RETORNO, ERRORES, EXCLUSIONES.
2. `pattern` valida el input antes de invocar la tool real.
3. `examples` ancla al modelo en el formato.
4. `additionalProperties: false` rechaza inputs inesperados.

## 🧪 Escenario de examen

**Pregunta tipo:** "Un agente tiene dos tools: `analyze_content` y `analyze_document`. Los devs notan que el modelo elige mal entre ambas el 35% de las veces. ¿Mejor solución?"

**Opciones:**
- A) Cambiar a un modelo más grande.
- B) Forzar `tool_choice: "auto"`.
- C) **Renombrar y reescribir descripciones para que sean específicas y mutuamente excluyentes** (qué tipo de input, qué retorno, cuándo NO usarla).
- D) Reducir `max_tokens` para forzar respuestas más cortas.

**Respuesta:** **C**. El misrouting viene de descripciones solapadas. Especificar input, output, y exclusiones lo resuelve casi siempre sin cambiar de modelo.
