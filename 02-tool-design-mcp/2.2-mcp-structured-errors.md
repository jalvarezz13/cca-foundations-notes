# 2.2 — Respuestas estructuradas de error en tools MCP

> **Dominio 2 — Tool Design & MCP Integration · 18% del examen**

---

## 🎯 Concepto clave

En MCP existen **dos planos de error**: errores de **protocolo** (JSON-RPC, fallos al hablar con el servidor) y errores de **ejecución de tool** (la tool corrió pero el resultado es un fallo lógico). Los segundos se marcan con el flag **`isError: true`** dentro del `tool_result`. Un mensaje genérico tipo "Operation failed" **mata la recuperación inteligente del modelo**. La práctica correcta es devolver **errores categorizados con metadata** (categoría, retryable, human-readable).

---

## 📚 Profundización

### Dos planos de error en MCP

| Plano | Cómo se manifiesta | Quién decide |
|---|---|---|
| **Protocol error** (JSON-RPC) | Excepción en el transporte; no llega `tool_result` al modelo. | El runtime / cliente. |
| **Tool execution error** | `tool_result` con `isError: true`. | La **tool** decide y lo señala. |

Ejemplo de un `tool_result` con error:
```json
{
  "type": "tool_result",
  "tool_use_id": "toolu_01ABC",
  "content": [{"type": "text", "text": "Order ORD-2024-3349 not found in our system."}],
  "isError": true
}
```

El modelo **ve** que falló y puede reaccionar (explicar al usuario, intentar otra tool, pedir más datos).

### Categorías sugeridas

Anthropic / MCP no fijan un enum oficial de categorías de error. La práctica canónica del examen distingue cuatro:

| Categoría | Causa típica | Retryable | Acción del agente |
|---|---|---|---|
| `transient` | Red, timeout, 5xx, rate limit | ✅ sí | Reintentar (con backoff) |
| `validation` | Input malformado o fuera de schema | ❌ no | Reformular input |
| `business` | Regla de negocio impide la operación | ❌ no | Explicar al usuario / escalar |
| `permission` | Sin acceso al recurso | ❌ no | Pedir credenciales o escalar |

### Por qué errores uniformes son tóxicos

🔴 **Caso "Operation failed":**
```json
{"isError": true, "content": [{"type": "text", "text": "Operation failed"}]}
```
El modelo:
- No puede decidir si reintentar o no.
- No puede explicar el problema al usuario.
- No puede elegir una tool alternativa.

→ Resultado típico: el agente devuelve "Lo siento, algo falló, inténtalo más tarde." Pésima UX.

🟢 **Mismo escenario con error estructurado:**
```json
{
  "isError": true,
  "content": [{
    "type": "text",
    "text": "Order ORD-2024-3349 not found. It may belong to a different account."
  }],
  "_meta": {
    "errorCategory": "not_found",
    "isRetryable": false,
    "suggestedAction": "ask_user_to_verify_order_id_or_login_to_correct_account"
  }
}
```
El modelo puede ahora **pedir al usuario que verifique el ID** o **revisar la cuenta logueada**.

### Recuperación local en subagentes

> Patrón canónico del examen: **resolver lo recuperable en el subagente; propagar al coordinador sólo lo no resoluble**.

Ejemplo: un subagente de research busca en una KB y la query devuelve `errorCategory: "rate_limited"`. El subagente debería:
1. Esperar y reintentar (recuperación local).
2. Sólo si tras N reintentos sigue fallando, propagar al coordinador con detalle.

Si el subagente propaga al coordinador toda transient error, el coordinador queda invadido de ruido recuperable y pierde su capacidad de orquestar.

### Fallo de acceso vs. resultado vacío

| Caso | Cómo se reporta | Significado |
|---|---|---|
| KB cayó / red rota | `isError: true`, `errorCategory: "transient"` | No pudimos comprobar; reintenta |
| KB OK, sin resultados | `isError: false`, `content: {"results": []}` | Sí comprobamos; no hay datos |

**Confundirlos es un error grave.** El examen pregunta este caso explícitamente.

## ⚠️ Anti-patrones

### 🔴 Errores con mensaje genérico
```json
{"isError": true, "content": [{"type":"text","text":"Error"}]}
```
El modelo no puede decidir nada.

### 🔴 Convertir "no results" en error
```python
if not results:
    return ToolResult(isError=True, content="no data")  # ❌
```
"No results" es un resultado válido; convertirlo en error rompe el razonamiento del modelo.

### 🔴 Suprimir errores silenciosamente
```python
try:
    return real_lookup(...)
except Exception:
    return ToolResult(content="")   # ❌ peor que el error genérico
```
El modelo no sabe que falló.

### 🔴 Categorías cambiantes según el día
Hoy `transient`, mañana `network_error`, pasado `temp_failure`. El modelo no aprende. Define un set cerrado y respétalo.

### 🔴 No incluir mensaje human-readable
Sólo metadata sin texto explicativo → el modelo no tiene cómo verbalizarlo al usuario.

## ✅ Patrón correcto

### Implementación de MCP tool con errores estructurados

```python
# Pseudo-código de una MCP tool en Python
from mcp.types import ToolResult, TextContent

def lookup_order(order_id: str) -> ToolResult:
    try:
        order = db.get_order(order_id)
    except Timeout:
        return ToolResult(
            isError=True,
            content=[TextContent(text=f"Timeout looking up order {order_id}.")],
            meta={
                "errorCategory": "transient",
                "isRetryable": True,
                "retryAfterMs": 1500,
            },
        )
    except PermissionDenied:
        return ToolResult(
            isError=True,
            content=[TextContent(text=f"Access denied to order {order_id}.")],
            meta={
                "errorCategory": "permission",
                "isRetryable": False,
                "suggestedAction": "verify_user_session",
            },
        )

    if order is None:
        # NO ES UN ERROR — es un resultado válido "no encontrado"
        return ToolResult(
            isError=False,
            content=[TextContent(text=f"No order found with ID {order_id}.")],
            meta={"resultType": "empty"},
        )

    if not order.customer_id == current_user.id:
        return ToolResult(
            isError=True,
            content=[TextContent(text=f"Order {order_id} does not belong to current user.")],
            meta={
                "errorCategory": "permission",
                "isRetryable": False,
            },
        )

    return ToolResult(
        isError=False,
        content=[TextContent(text=json.dumps(order.to_dict()))],
    )
```

### Recuperación local en subagente

```python
# Subagente con retry para transient errors
async def fetch_with_retry(tool_name, args, max_retries=3):
    for attempt in range(max_retries):
        result = await call_tool(tool_name, args)
        if not result.isError:
            return result
        category = result.meta.get("errorCategory")
        if category != "transient":
            return result  # propagar inmediatamente
        await asyncio.sleep(2 ** attempt)  # backoff exponencial
    return result  # propagar tras agotar retries
```

## 🧪 Escenario de examen

**Pregunta tipo:** "Una MCP tool devuelve `{isError: true, content: [{text: 'Operation failed'}]}` en cualquier fallo. El equipo nota que el agente abandona casos legítimos donde un retry o un input distinto resolverían. ¿Mejor solución?"

**Opciones:**
- A) Reducir el timeout para que falle más rápido.
- B) **Devolver errores estructurados con categoría (`transient` / `validation` / `business` / `permission`), retryable y mensaje human-readable.**
- C) Quitar el flag `isError` para que el modelo no lo vea.
- D) Capturar los errores en el coordinador y siempre reintentar.

**Respuesta:** **B**. La causa raíz es la pérdida de información: el modelo no puede decidir si reintentar, reformular o escalar. Estructurar el error le da las palancas para razonar correctamente. **D** es peligrosa porque reintenta también errores no recuperables (gastando coste).
