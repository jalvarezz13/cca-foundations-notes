# 2.3 — Distribución de tools entre agentes y `tool_choice`

> **Dominio 2 — Tool Design & MCP Integration · 18% del examen**

---

## 🎯 Concepto clave

**Demasiadas tools degradan la fiabilidad de selección** del modelo. La distribución correcta es: cada agente sólo ve las tools que necesita para su rol, con quizá un puñado adicional de "cross-role" para casos frecuentes. Para forzar comportamiento, **`tool_choice`** controla si el modelo decide (`auto`), es obligado a usar alguna tool (`any`), debe usar una específica (`tool` por nombre) o no puede usar tools (`none`).

---

## 📚 Profundización

### Coste de tener demasiadas tools

| Nº tools | Acierto típico de selección | Notas |
|---|---|---|
| 4-5 | ~98% | Sweet spot |
| 8-10 | ~90% | Aceptable |
| 15-20 | ~70-80% | Misrouting evidente |
| 30+ | <60% | Inutilizable |

> El examen menciona explícitamente el contraste **18 tools vs 4-5 tools**. Reducir es ganar.

**Por qué degrada:**
- Más opciones → más overlap entre descripciones → ambigüedad.
- El prompt crece → "lost in the middle" para las tools del medio.
- El modelo tiende a sobre-explorar (intenta varias tools "por si acaso").

### Estrategia de scoping por rol

```
ROL: customer_support_agent
  - lookup_order
  - verify_identity
  - issue_refund (gated)
  - change_address
  - escalate_to_human

ROL: billing_specialist
  - lookup_invoice
  - update_payment_method
  - issue_refund (gated)
  - generate_payment_link

ROL: shipment_tracker
  - lookup_tracking
  - request_redelivery
  - update_shipping_address

CROSS-ROLE (en todos por frecuencia):
  - search_kb
  - escalate_to_human
```

**Reglas:**
- Cada agente ve **5-7 tools** como máximo.
- Cross-role tools sólo si la frecuencia de uso lo justifica (ej. >20% de las sesiones).
- Tools sensibles (`issue_refund`) **gated por hook** independientemente del agente.

### `tool_choice` — 4 valores

```python
# 1) auto — DEFAULT. El modelo decide si usar tools o responder en texto.
tool_choice = "auto"

# 2) any — FUERZA usar alguna tool (cualquiera). No emite preámbulo natural.
tool_choice = "any"

# 3) tool por nombre — FUERZA esa tool específica.
tool_choice = {"type": "tool", "name": "extract_invoice_data"}

# 4) none — Prohíbe tools. Sólo respuesta en texto.
tool_choice = "none"
```

**Reglas que el examen evalúa:**

- `auto` es el **default**. Apto para conversación abierta.
- `any` quita los preámbulos naturales ("Let me check that..."). El modelo va directo a una tool.
- `tool` (forzado por nombre) es la opción para **output estructurado garantizado** (ver Dominio 4.3).
- `none` para cuando quieres respuesta en texto pero el contexto incluye tools por compatibilidad.
- **Con extended thinking**, sólo `auto` y `none` son compatibles. `any` y `tool` **NO**.

### Reemplazar tools genéricas por alternativas restringidas

Ejemplo: tu agente puede acceder a documentos internos. Hay dos diseños:

🔴 Genérica y peligrosa:
```json
{
  "name": "fetch_url",
  "description": "Fetches any URL and returns its content."
}
```
→ El agente puede acceder a **cualquier** URL: SSRF, exfiltración, alcance no auditable.

🟢 Restringida:
```json
{
  "name": "load_document",
  "description": "Loads a document from the internal catalog by its ID.",
  "input_schema": {
    "properties": {
      "document_id": {"type": "string", "pattern": "^DOC-\\d+$"}
    }
  }
}
```
→ Sólo accede al catálogo. Auditable, scopeable, sin SSRF.

### Tools cross-role limitadas

Para necesidades genuinamente compartidas (KB search, escalation), usar **un único** nombre canónico y compartirlo. Evita variaciones por agente que generen confusión en logs y métricas.

## ⚠️ Anti-patrones

### 🔴 "Dale todas las tools por si acaso"
```python
agent.allowed_tools = ALL_TOOLS  # ❌ 25+ tools
```
Sí, el modelo puede usar cualquiera; no, no las usará bien.

### 🔴 `tool_choice = "any"` con extended thinking
Combinación no soportada → error de API.

### 🔴 Forzar tool por nombre cuando puede ser mala elección
```python
tool_choice = {"type":"tool","name":"refund"}  # ❌ aunque el caso no aplique
```
Forzar tools sólo cuando estás seguro de que ese turno debe terminar con esa tool (ej. extracción estructurada).

### 🔴 Cross-role tools con nombres distintos en cada agente
- En `support_agent`: `kb_search`
- En `billing_agent`: `search_knowledge_base`
- En `triage_agent`: `lookup_docs`

→ Métricas fragmentadas, debugging duro, prompts inconsistentes.

### 🔴 Tools potentes accesibles sin gate
`execute_sql`, `send_email`, `delete_record` sin `PreToolUse` hook → daño irreversible.

## ✅ Patrón correcto

### Distribución por rol + tool_choice según uso

```python
# Definición de agentes
support_agent = AgentDefinition(
    description="Customer support: orders, refunds, address changes.",
    prompt=SUPPORT_PROMPT,
    tools=[
        "lookup_order",
        "verify_identity",
        "issue_refund",      # gated por hook
        "change_address",
        "escalate_to_human", # cross-role
        "search_kb",         # cross-role
    ],
)

extractor_agent = AgentDefinition(
    description="Document data extractor: returns structured JSON.",
    prompt=EXTRACTOR_PROMPT,
    tools=["extract_invoice_data"],  # sólo una
)

# Diferentes tool_choice según el caso
# Conversación abierta
response_conv = client.messages.create(
    model="claude-opus-4-5",
    messages=msgs,
    tools=support_tools,
    tool_choice="auto",
)

# Extracción estructurada FORZADA
response_extract = client.messages.create(
    model="claude-opus-4-5",
    messages=[{"role": "user", "content": pdf_text}],
    tools=[EXTRACT_INVOICE_TOOL],
    tool_choice={"type": "tool", "name": "extract_invoice_data"},
)
```

### Tabla de decisión

| Situación | `tool_choice` |
|---|---|
| Conversación abierta | `auto` |
| Workflow donde el siguiente paso debe usar alguna tool sí o sí | `any` |
| Extracción estructurada a JSON schema | `{"type":"tool","name":"..."}` |
| Quiero respuesta en lenguaje natural; tools sólo de compat | `none` |
| Extended thinking activado | sólo `auto` / `none` |

## 🧪 Escenario de examen

**Pregunta tipo:** "Un agente tiene 18 tools registradas. Misrouting alcanza el 25%. Tras analizar logs, vemos que 6 de esas tools nunca se han usado, otras 4 son variantes casi idénticas, y sólo 4 cubren el 80% de las invocaciones. ¿Mejor solución?"

**Opciones:**
- A) Subir el modelo.
- B) Añadir más few-shot examples al system prompt.
- C) **Reducir el set a 4-5 tools por rol: eliminar las no usadas, unificar las variantes, scopear por agente. Las menos frecuentes se exponen sólo en agentes especializados.**
- D) Usar `tool_choice="any"` para forzar siempre alguna tool.

**Respuesta:** **C**. El problema raíz es **sobrecarga**, no falta de instrucción. **D** sólo cambia "usa alguna" pero no resuelve el misrouting entre las muchas tools restantes.
