# 2.4 — Integración de servidores MCP en Claude Code

> **Dominio 2 — Tool Design & MCP Integration · 18% del examen**

---

## 🎯 Concepto clave

**Model Context Protocol (MCP)** es un protocolo abierto que estandariza cómo Claude se conecta a fuentes externas. En Claude Code la configuración vive en dos archivos: `.mcp.json` para alcance **proyecto** (versionado en git) y `~/.claude.json` para alcance **usuario** (personal). Soporta **variables de entorno** para credenciales. Cada servidor MCP expone **tools** (funciones ejecutables) y **resources** (datos/contexto).

---

## 📚 Profundización

### Scoping: proyecto vs usuario

| Archivo | Scope | Versiona en git | Para |
|---|---|---|---|
| `.mcp.json` (raíz del proyecto) | **Proyecto** | ✅ sí | Servidores compartidos con el equipo |
| `~/.claude.json` | **Usuario** | ❌ no | Servidores personales (tu Jira, tu Linear, etc.) |

> **Trampa de examen:** `~/.mcp.json` **no existe**. El user-level es `~/.claude.json`.

### Estructura de `.mcp.json`

```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    },
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/var/log"],
      "env": {}
    },
    "atlassian": {
      "command": "npx",
      "args": ["-y", "mcp-atlassian"],
      "env": {
        "JIRA_URL": "${JIRA_URL}",
        "JIRA_TOKEN": "${JIRA_TOKEN:-no-token}"
      }
    }
  }
}
```

### Expansión de variables de entorno

| Sintaxis | Comportamiento |
|---|---|
| `${VAR}` | Toma el valor de `VAR` del entorno; falla si no existe |
| `${VAR:-default}` | Toma `VAR` si existe, si no `default` |

> **Buenas prácticas:**
> - Credenciales **siempre** vía `${}`, no hardcodeadas.
> - Documentar las variables requeridas en el `README` del repo.
> - `.env.example` con los nombres (no valores).

### Tools y Resources de un MCP server

Cada servidor expone dos capabilities:

| Capability | Qué es | Quién decide invocar |
|---|---|---|
| `tools` | Funciones ejecutables (`create_issue`, `get_file`) | El modelo (model-controlled) |
| `resources` | Datos/contexto expuestos por URI (`schema://...`, `issue://JIRA-123`) | App o modelo (app/model-driven) |

**Cuándo usar Resources en lugar de Tools:**
- Catálogos de contenido que el modelo va a citar (issues, docs, schemas).
- Datos relativamente estáticos que no necesitan ejecución.
- Reduce **tool calls exploratorios**: el modelo ve los resources disponibles en el listing y no tiene que "buscar".

Ejemplo:
- 🔴 Sin resources: el agente hace `tool: list_jira_projects` → `tool: list_issues_in_project` → `tool: get_issue` (3 tool calls).
- 🟢 Con resources: `resources` lista `issue://PROJ-N/123`, `issue://PROJ-N/124`. El modelo accede directo sin tool exploratoria.

### Disponibilidad simultánea de tools

**Todas las tools de los MCP servers configurados quedan disponibles a la vez.** El modelo las ve todas en cada turno.

Implicación: si tienes 3 MCP servers con 6 tools cada uno → 18 tools en el prompt. Empieza a sufrir el problema del Dominio 2.3 (demasiadas tools degradan selección). **Distribución por agente**:

- Coordinator → ve resources (catálogos) pero pocas tools.
- Subagent_github → ve sólo las 4 tools de github.
- Subagent_jira → ve sólo las 5 tools de atlassian.

### Preferir servidores comunitarios para integraciones estándar

> Si necesitas integración con **Jira / Confluence / GitHub / Slack / Postgres / Filesystem**, **NO escribas tu propio MCP server**. Usa el oficial / comunitario.

Razones:
- Ya manejan errores estructurados (`isError`, categorías).
- Mantenidos contra cambios de la API externa.
- Patrones probados para auth, paginación, rate limits.
- Reduce superficie de bugs propios.

Repo oficial de referencias: <https://github.com/modelcontextprotocol/servers>

Servidores comunes:
| Servidor | Repo | Uso |
|---|---|---|
| `server-filesystem` | oficial | Acceso a directorios locales |
| `server-github` | oficial | PR, issues, files |
| `server-postgres` | oficial | Queries SQL read-only |
| `mcp-atlassian` | comunidad | Jira + Confluence |
| `server-everything` | oficial demo | Showcase de todas las capabilities |

## ⚠️ Anti-patrones

### 🔴 Credenciales hardcodeadas en `.mcp.json`
```json
{
  "env": {"GITHUB_TOKEN": "ghp_real_secret_committed_to_git"}
}
```
Filtra al historial de git, a forks, a CI logs.

### 🔴 Confundir `~/.claude.json` con `~/.mcp.json`
El segundo **no existe**. Usar el primero (con prefijo claude).

### 🔴 Construir tu propio MCP server para integraciones estándar
Reinventas error handling, auth refresh, rate limits, paginación. Coste alto, valor bajo.

### 🔴 Tener todos los MCP servers activados a la vez en un solo agente
Si tu coordinador ve 30 tools, el routing se rompe.

### 🔴 Exponer un MCP server con scope demasiado amplio
`server-filesystem` apuntando a `/` → acceso a TODO. Apunta a directorios específicos.

## ✅ Patrón correcto

### `.mcp.json` para un proyecto con varios servers

```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    },
    "atlassian": {
      "command": "npx",
      "args": ["-y", "mcp-atlassian"],
      "env": {
        "JIRA_URL": "${JIRA_URL}",
        "JIRA_TOKEN": "${JIRA_TOKEN}",
        "CONFLUENCE_URL": "${CONFLUENCE_URL:-${JIRA_URL}/wiki}"
      }
    },
    "fs-logs": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-filesystem",
        "/var/log/myapp"
      ],
      "env": {}
    }
  }
}
```

### Distribución por subagente

```python
agents = {
    "github-investigator": AgentDefinition(
        description="Searches GitHub PRs/issues/files for a fix or feature.",
        prompt="...",
        tools=["github_search_code", "github_get_pr", "github_list_issues"],  # sólo github
    ),
    "jira-investigator": AgentDefinition(
        description="Searches Jira for related tickets and project status.",
        prompt="...",
        tools=["jira_search", "jira_get_issue"],  # sólo atlassian
    ),
    "log-analyzer": AgentDefinition(
        description="Reads recent logs to identify error patterns.",
        prompt="...",
        tools=["fs_read", "fs_list"],  # sólo filesystem
    ),
}
```

Coordinador delega a cada subagente según el aspecto del problema.

### `.env.example` documentando variables

```bash
# Required for github MCP server
GITHUB_TOKEN=ghp_yourtoken

# Required for atlassian MCP server
JIRA_URL=https://yourcompany.atlassian.net
JIRA_TOKEN=ATATT3xFfGF0...

# Optional — defaults to ${JIRA_URL}/wiki
# CONFLUENCE_URL=
```

## 🧪 Escenario de examen

**Pregunta tipo:** "Necesitas integrar Jira en Claude Code para todo el equipo. El equipo ya usa MCP. ¿Mejor enfoque?"

**Opciones:**
- A) Escribir un MCP server propio en Python para tener control total.
- B) **Añadir el servidor MCP comunitario de Atlassian a `.mcp.json` con credenciales vía variables de entorno, y commitear el `.mcp.json` (sin secretos).**
- C) Pegar los tickets manualmente en el prompt.
- D) Crear una tool personalizada que llame a la API de Jira con `requests`.

**Respuesta:** **B**. Usa el servidor existente (mantenido, probado). Versiona la configuración (compartida con el equipo). Las credenciales quedan fuera de git por la indirección con `${VAR}`.
