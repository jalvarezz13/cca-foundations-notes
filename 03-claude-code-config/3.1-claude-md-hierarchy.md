# 3.1 — Archivos CLAUDE.md: jerarquía, scope y organización modular

> **Dominio 3 — Claude Code Configuration & Workflows · 20% del examen**

---

## 🎯 Concepto clave

`CLAUDE.md` es el archivo de memoria de Claude Code: instrucciones, convenciones y contexto que **se cargan automáticamente** al iniciar una sesión. Existe en **tres niveles** jerárquicos con scopes distintos: usuario, proyecto, y local. La sintaxis **`@import`** permite modularizar archivos largos; el directorio **`.claude/rules/`** ofrece una alternativa estructurada al monolito.

---

## 📚 Profundización

### Jerarquía de carga (de más general a más específico)

```
1. ~/.claude/CLAUDE.md           ← USUARIO  (personal, NO versionado)
2. ./CLAUDE.md  o  ./.claude/CLAUDE.md   ← PROYECTO (versionado en git)
3. ./CLAUDE.local.md             ← LOCAL del proyecto (gitignored, personal)
4. subdir/CLAUDE.md              ← bajo demanda al leer archivos en subdir/
```

> Las dos ubicaciones del nivel de proyecto (`./CLAUDE.md` y `./.claude/CLAUDE.md`) son equivalentes. Usa una u otra según tu preferencia organizativa.

| Nivel | Path | Versionado | Quién lo edita |
|---|---|---|---|
| Usuario | `~/.claude/CLAUDE.md` | ❌ | Sólo tú |
| Proyecto | `./CLAUDE.md` o `./.claude/CLAUDE.md` | ✅ git | Todo el equipo |
| Local | `./CLAUDE.local.md` | ❌ (gitignored) | Tú en este proyecto |
| Subdirectorio | `<dir>/CLAUDE.md` | ✅ git | Equipo, scope local |

### Carga bajo demanda en subdirectorios

Los archivos `CLAUDE.md` en subdirectorios **NO** se cargan al inicio. Se cargan automáticamente **cuando Claude lee un archivo dentro** (o debajo) de ese directorio.

```
repo/
├── CLAUDE.md                    ← carga al inicio
├── src/
│   ├── billing/
│   │   ├── CLAUDE.md            ← carga cuando se toca algo bajo src/billing/
│   │   └── invoice.ts
│   └── auth/
│       ├── CLAUDE.md            ← carga cuando se toca algo bajo src/auth/
│       └── jwt.ts
```

Ventaja: contexto **just-in-time**, no se infla el prompt con reglas irrelevantes.

### Sintaxis `@import`

Permite incluir otros archivos markdown en el `CLAUDE.md`:

```markdown
# Project conventions

@AGENTS.md
@docs/coding-style.md
@docs/testing-conventions.md

## Specific to this repo
- Use vitest, not jest.
- All HTTP handlers go under `src/api/`.
```

**Reglas oficiales:**
- Path **relativo al archivo** que hace `@import`.
- Hasta **5 niveles** de anidamiento (no más).
- Sin extensión también funciona (`@AGENTS` busca `AGENTS.md`).
- No hay carga condicional con `@import` — siempre se carga.

### Alternativa: `.claude/rules/`

Para configuraciones grandes, un directorio con archivos por tema:

```
.claude/rules/
├── general.md           ← se carga siempre (sin frontmatter)
├── testing.md           ← se carga sólo al editar tests
└── api.md               ← se carga sólo al editar src/api/
```

```markdown
---
paths:
  - "src/**/*.test.ts"
  - "tests/**/*.ts"
---
# Testing conventions
- Use vitest
- Mocks via `vi.mock()`
- ...
```

> Las **rules** con frontmatter `paths` son carga condicional. Las sin `paths` se cargan al inicio. **Más detalle en 3.3**.

### Comando `/memory`

Dentro de Claude Code, escribir `/memory` muestra **qué archivos de memoria están actualmente cargados** en la sesión, en qué orden, y de qué nivel vienen.

Útil para debugging cuando una convención no se está aplicando: comprueba si el archivo de reglas está cargado.

## ⚠️ Anti-patrones

### 🔴 Monolito gigante con todas las convenciones

```
# 1 sólo CLAUDE.md de 1500 líneas
```
Difícil de mantener, infla el contexto, mezcla concerns. Mejor: dividir con `@import` o usar `.claude/rules/`.

### 🔴 Convenciones personales en `./CLAUDE.md`

Si pones tu preferencia de tabs vs spaces en `./CLAUDE.md`, **lo impones a todo el equipo**. Las preferencias personales van en `~/.claude/CLAUDE.md` (user) o `./CLAUDE.local.md` (local, gitignored).

### 🔴 Versionar `./CLAUDE.local.md`

Está pensado para overrides personales del proyecto. **Añádelo a `.gitignore`** y verifica que no lo subes.

### 🔴 Subdirectorio `CLAUDE.md` con reglas globales

Si la convención aplica a todo el repo, ponla en el raíz. Sólo usa subdir para reglas **estrictamente locales** a ese módulo.

### 🔴 Reglas de codestyle en CLAUDE.md cuando es responsabilidad del linter

Si tu linter ya enforce algo, NO lo duplicas en `CLAUDE.md`. Coste de mantenimiento doble.

## ✅ Patrón correcto

### Estructura modular para un proyecto medio

```
repo/
├── CLAUDE.md
├── .claude/
│   └── rules/
│       ├── testing.md           # paths: **/*.test.ts
│       ├── api-handlers.md      # paths: src/api/**/*.ts
│       └── billing.md           # paths: src/billing/**/*.ts
├── AGENTS.md                    # importado por CLAUDE.md
└── docs/
    └── coding-style.md          # importado por CLAUDE.md
```

`CLAUDE.md`:
```markdown
# Project: my-saas

This is a TypeScript Node.js SaaS. Stripe for billing, Postgres for DB.

@AGENTS.md
@docs/coding-style.md

## Architecture notes
- Domain logic under `src/domain/`.
- HTTP under `src/api/`.
- Stripe webhooks under `src/api/webhooks/stripe.ts`.

## Commands
- Tests: `npm test`
- Lint: `npm run lint`
- Type-check: `npm run typecheck`
```

`AGENTS.md`:
```markdown
# Agent conventions
- Always run `npm run typecheck` after edits.
- Never modify `src/generated/` (regenerated).
- Use vitest, never jest.
```

## 🧪 Escenario de examen

**Pregunta tipo:** "Un equipo quiere que las convenciones de testing aplicarán **sólo** cuando se editen archivos `*.test.ts`. Tienen un único `CLAUDE.md` monolítico con todo dentro. ¿Mejor solución?"

**Opciones:**
- A) Duplicar el `CLAUDE.md` en cada subdirectorio que contenga tests.
- B) **Crear `.claude/rules/testing.md` con frontmatter `paths: ["**/*.test.ts"]`** para que sólo se cargue cuando se toquen tests.
- C) Borrar la sección de testing del `CLAUDE.md` y poner en `~/.claude/CLAUDE.md`.
- D) Pedirle al modelo en cada turno que recuerde las reglas de testing.

**Respuesta:** **B**. Es exactamente lo que las path-specific rules resuelven: contexto just-in-time, no se infla el prompt cuando no aplica, versionado en el repo. **A** funciona pero duplica trabajo. **C** la limita a tu usuario, no al equipo.
