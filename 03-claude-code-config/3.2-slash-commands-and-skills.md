# 3.2 — Slash commands y Skills personalizados

> **Dominio 3 — Claude Code Configuration & Workflows · 20% del examen**

---

## 🎯 Concepto clave

Los **slash commands** (`/deploy`, `/review`) son invocaciones explícitas del usuario, y las **Skills** son capacidades discoverables que el modelo invoca on-demand cuando reconoce un caso de uso. En versiones recientes de Claude Code **commands y skills convergieron**: tanto `.claude/commands/deploy.md` como `.claude/skills/deploy/SKILL.md` registran `/deploy`. La elección entre ambos depende de si quieres invocación explícita del usuario, descubrimiento por el modelo, o ambas.

---

## 📚 Profundización

### Ubicaciones de Skills y Commands

```
~/.claude/commands/        ← user-scoped commands (personal)
~/.claude/skills/<name>/   ← user-scoped skills (personal)

.claude/commands/          ← project-scoped commands (versionado)
.claude/skills/<name>/     ← project-scoped skills (versionado)
```

| Path | Scope | Versionado | Compartido con equipo |
|---|---|---|---|
| `~/.claude/commands/` | Usuario | ❌ | No |
| `~/.claude/skills/` | Usuario | ❌ | No |
| `.claude/commands/` | Proyecto | ✅ | Sí |
| `.claude/skills/` | Proyecto | ✅ | Sí |

### Convergencia commands ↔ skills

Tanto:
```
.claude/commands/deploy.md
```
como:
```
.claude/skills/deploy/SKILL.md
```
crean el slash command `/deploy`. La forma de Skill (directorio) es preferible para skills complejas porque permite **bundles de assets**: scripts, templates, referencias dentro del mismo directorio.

```
.claude/skills/deploy/
├── SKILL.md         ← instrucciones principales
├── deploy.sh        ← script auxiliar
├── rollback.sh      ← script auxiliar
└── templates/
    └── changelog.md
```

### Anatomía de un Skill (`SKILL.md`)

```markdown
---
name: pr-summary
description: Summarize the changes in a pull request, suitable for posting as a PR description.
context: fork
allowed-tools: Bash(gh *), Read, Grep
argument-hint: "<pr-number>"
disable-model-invocation: false
user-invocable: true
---

# PR Summary

You are summarizing PR #${1} of the current repo. Steps:

1. Run `gh pr view ${1} --json title,body,files,commits`.
2. Read each changed file with `Read`.
3. Group changes by area (api / domain / tests / docs).
4. Output:
   ## Summary
   - bullet 1
   - bullet 2
   ## Files changed
   ...
```

### Frontmatter — campos

| Campo | Propósito |
|---|---|
| `name` | Nombre del skill / slug del comando (`/pr-summary`). |
| `description` | **Crítico.** Lo lee el modelo para decidir invocación on-demand. Sé específico. |
| `context: fork` | Ejecuta en **subagente aislado** — el output verboso no contamina la sesión principal. |
| `allowed-tools` | Whitelist de tools (lista o glob). Limita lo que el skill puede hacer. |
| `argument-hint` | Pista al usuario / modelo sobre los argumentos esperados. |
| `disable-model-invocation` | Si `true`, sólo invocable explícitamente con `/name`, el modelo no puede llamarlo. |
| `user-invocable` | Si `true`, aparece como `/name` también. |

### `context: fork` — por qué importa

> Si una skill genera **mucho output** (ej. `pr-summary` lee 30 archivos), correrla en la sesión principal infla el contexto. Con `context: fork`, la skill se ejecuta en un **subagente aislado** y sólo devuelve el resultado final a la sesión principal.

Resultado:
- Sesión principal limpia (sólo el output del skill).
- Sub-sesión hace toda la exploración verbosa.
- Token efficiency masiva.

### Skill vs `CLAUDE.md`

| Aspecto | Skill | `CLAUDE.md` |
|---|---|---|
| Carga | On-demand | Siempre cargado |
| Coste de tokens en sesión normal | 0 | constante |
| Adecuado para | Workflows ocasionales con muchos pasos | Convenciones de codestyle aplicables siempre |
| Ejemplos | `/deploy`, `/release`, `/pr-summary`, `/scaffold` | "Use vitest", "Run typecheck after edits" |

### Variante personal del mismo skill

Si el equipo tiene una skill `/deploy` en `.claude/skills/deploy/`, **tú** puedes tener tu propia versión en `~/.claude/skills/my-deploy/` (otro nombre) para no chocar. O usar el frontmatter `name:` para evitar colisión.

> No sobrescribas la skill del equipo. Crea variante.

## ⚠️ Anti-patrones

### 🔴 Skills sin `description` o con descripción vaga

```yaml
---
name: thing
description: Does stuff
---
```
El modelo nunca la invoca. La `description` es el mecanismo de discovery.

### 🔴 Skills verbosas en `context` principal

Sin `context: fork`, una skill que lee 50 archivos llena el prompt. Aplica `context: fork`.

### 🔴 Skills con `allowed-tools` excesivo

`allowed-tools: *` da acceso ilimitado al subagente. Acota.

### 🔴 Confundir `.claude/commands/` con `~/.claude/commands/`

El primero es del proyecto (todos lo ven), el segundo es personal. Subir tu shortcut personal al repo del equipo causa confusión.

### 🔴 Convertir todo en slash command

Si una convención aplica **siempre** (estilo, naming), va en `CLAUDE.md` o `.claude/rules/`, no en una skill.

## ✅ Patrón correcto

### Skill `/release` con `context: fork`

```
.claude/skills/release/
├── SKILL.md
└── checklist.md
```

`SKILL.md`:
```markdown
---
name: release
description: Create a release tag for the current branch. Runs tests, bumps version, generates changelog, and creates GitHub release. Use after merging release-ready PRs.
context: fork
allowed-tools: Bash(npm *), Bash(git *), Bash(gh *), Read, Edit
argument-hint: "<major|minor|patch>"
---

# Release skill

Steps:

1. Confirm clean working tree (`git status`).
2. Run tests: `npm test`. Abort on failure.
3. Bump version: `npm version ${1:-patch}`.
4. Read `CHANGELOG.md` and prepend entries from `git log v<prev>..HEAD`.
5. `git push --follow-tags`.
6. `gh release create v<new>` with the changelog excerpt.
7. Output a 1-line summary: "Released v<new>".

@checklist.md
```

`checklist.md` (asset bundled):
```markdown
## Release checklist
- [ ] CHANGELOG entries grouped by type (feat, fix, chore).
- [ ] Breaking changes labeled clearly.
- [ ] Migration notes if schema changed.
```

### Slash command personal (`~/.claude/commands/pr-template.md`)

```markdown
---
name: pr-template
description: Generate a PR description using the team's standard template.
---

Generate a PR description following this template:

## Summary
<1-3 bullets>

## Test plan
<steps>

## Risk
<low/medium/high + why>

Use the current branch's commits to fill it.
```

## 🧪 Escenario de examen

**Pregunta tipo:** "El equipo quiere automatizar el flujo `/deploy` que: lee 20 archivos de config, hace varios checks, genera changelog y publica. Notan que después de invocar `/deploy`, la sesión principal queda llena de output que entorpece las siguientes interacciones. ¿Mejor solución?"

**Opciones:**
- A) Reducir la cantidad de archivos que lee `/deploy`.
- B) Eliminar `/deploy` y hacer los pasos manuales.
- C) **Añadir `context: fork` al frontmatter del Skill `/deploy`** para que se ejecute en subagente aislado y sólo devuelva el resultado final a la sesión principal.
- D) Usar `/compact` después de cada `/deploy`.

**Respuesta:** **C**. Es exactamente el patrón canónico de Skills verbosas: `context: fork` aísla la exploración. **D** funciona pero es reactivo y manual; **C** lo soluciona estructuralmente.
