# 3.3 — Reglas path-specific para carga condicional

> **Dominio 3 — Claude Code Configuration & Workflows · 20% del examen**

---

## 🎯 Concepto clave

Las reglas en `.claude/rules/` con frontmatter YAML **`paths`** se cargan **sólo cuando Claude edita archivos que matchean** los globs especificados. Esto resuelve el problema de tener convenciones que aplican a archivos **dispersos** por el repo (tests, mocks, schemas, configs) sin inflar el contexto en sesiones que no los tocan.

---

## 📚 Profundización

### Estructura

```
.claude/rules/
├── general.md           ← sin paths → carga siempre
├── testing.md           ← paths: ["**/*.test.ts", "**/*.test.tsx"]
├── api.md               ← paths: ["src/api/**/*.ts"]
├── generated.md         ← paths: ["src/generated/**"]
└── migrations.md        ← paths: ["db/migrations/**/*.sql"]
```

### Frontmatter

```markdown
---
paths:
  - "**/*.test.ts"
  - "**/*.test.tsx"
---

# Testing conventions
- Use vitest, NOT jest.
- Mocks via `vi.mock()`.
- One test file per source file, mirroring the directory.
- ...
```

| Campo | Comportamiento |
|---|---|
| Sin `paths` | Carga al inicio de la sesión, como `CLAUDE.md`. |
| Con `paths: [globs]` | Carga sólo cuando Claude **lee o edita** archivos que matchean. |

### Por qué `.claude/rules/` vence al `CLAUDE.md` por subdirectorio

Caso típico: las convenciones de test aplican a `**/*.test.ts`, pero los tests están **dispersos** por todo el repo (junto a las fuentes, no en una sola carpeta).

🔴 **Con `CLAUDE.md` por subdirectorio:**
- Tendrías que poner un `CLAUDE.md` en CADA carpeta que contenga tests.
- Si la carpeta también tiene producción, las reglas de test contaminan la sesión cuando se edita producción.
- Mantener N copias del mismo `CLAUDE.md` es un fail.

🟢 **Con `.claude/rules/testing.md` + `paths`:**
- Un solo archivo central.
- Carga **sólo** cuando se toca un `*.test.ts`, independientemente de dónde esté.
- Una sola fuente de verdad.

### Comportamiento de la carga

```
Sesión inicia
  → Carga: CLAUDE.md (siempre)
  → Carga: .claude/rules/general.md (siempre)

Usuario pide: "Edita src/api/users.ts"
  → Read src/api/users.ts
  → Auto-carga: .claude/rules/api.md (matchea src/api/**)

Usuario pide: "Añade un test"
  → Read src/api/users.test.ts
  → Auto-carga: .claude/rules/testing.md (matchea **/*.test.ts)

Usuario pide: "Genera una migración SQL"
  → Read db/migrations/0012_add_index.sql
  → Auto-carga: .claude/rules/migrations.md
```

### Globs soportados

Las `paths` aceptan globs estilo gitignore / glob estándar:

| Pattern | Match |
|---|---|
| `**/*.test.ts` | cualquier archivo `.test.ts` en cualquier nivel |
| `src/api/**` | todo dentro de `src/api/` |
| `*.md` | sólo en raíz |
| `**/migrations/**/*.sql` | SQL bajo cualquier carpeta `migrations` |
| `!src/legacy/**` | exclusión (algunas implementaciones) |

### Cuándo SÍ usar `.claude/rules/`

- Tests dispersos (`*.test.ts` por todo el repo).
- Archivos generados (`src/generated/`, `**/*.gen.ts`).
- Migraciones DB.
- Documentación específica (`docs/api/**`).
- Configs sensibles que requieren cuidado (`infra/**`).

### Cuándo usar `CLAUDE.md` (no rules)

- Convenciones globales que aplican a **todo** archivo del repo.
- Información de arquitectura, comandos del proyecto.
- Referencias a documentos importantes.

### Cuándo usar `<subdir>/CLAUDE.md`

- Cuando un módulo grande tiene reglas **estructurales** propias (ej. `src/billing/` con su propio README de arquitectura) Y el módulo está en una sola carpeta.

## ⚠️ Anti-patrones

### 🔴 Reglas globales con `paths`
```yaml
---
paths: ["**/*"]
---
```
Si aplica a todo, **no necesita** `paths`. Quítalo y se carga al inicio (mismo efecto, menos sobrecarga).

### 🔴 Una sola regla con paths para cosas no relacionadas
```yaml
---
paths: ["**/*.test.ts", "db/migrations/**", "src/api/**"]
---
```
Mezcla concerns. Tres reglas separadas son más fáciles de mantener.

### 🔴 `paths` ignorando case en sistemas case-sensitive
Linux es case-sensitive. `**/*.TS` no matchea `foo.ts`. Usar minúsculas y verificar.

### 🔴 Esperar que cargue antes de la primera lectura del path
La regla carga **al leer/editar** el archivo. No la veas activa antes.

### 🔴 Duplicar info entre rules y CLAUDE.md
Si "use vitest" está en `CLAUDE.md` Y en `rules/testing.md`, tienes dos fuentes de verdad. Decide una.

## ✅ Patrón correcto

### Setup completo de path-specific rules

```
repo/
├── CLAUDE.md
└── .claude/
    └── rules/
        ├── testing.md
        ├── api-handlers.md
        ├── generated.md
        └── stripe-webhooks.md
```

`testing.md`:
```markdown
---
paths:
  - "**/*.test.ts"
  - "**/*.test.tsx"
  - "**/__tests__/**/*.ts"
---
# Test conventions

- Use **vitest**, never jest. Import from `vitest`.
- Use `vi.mock(...)` for mocks (no `jest.mock`).
- One file per source file: `foo.ts` → `foo.test.ts`.
- Test names describe behavior: `should X when Y`.
- Use `beforeEach` for setup, not module-level state.
```

`generated.md`:
```markdown
---
paths:
  - "src/generated/**"
  - "**/*.gen.ts"
---
# Generated files — DO NOT EDIT

These files are generated by `npm run codegen`. Any change here is overwritten on the next regen.

If something needs changing, edit the source template under `codegen/templates/` and regenerate.
```

`stripe-webhooks.md`:
```markdown
---
paths:
  - "src/api/webhooks/stripe**.ts"
---
# Stripe webhook handlers

- Verify signature with `stripe.webhooks.constructEvent`.
- Return 200 quickly; enqueue work to background job.
- Idempotency: check `event.id` in `processed_events` table.
- Use the same `Stripe` instance from `src/lib/stripe.ts`.
```

## 🧪 Escenario de examen

**Pregunta tipo:** "Los tests del repo están dispersos junto a las fuentes (`src/foo.test.ts`, `src/billing/invoice.test.ts`, etc.). El equipo quiere que las convenciones de testing se carguen **sólo** cuando Claude edite tests, no en todas las sesiones. ¿Mejor solución?"

**Opciones:**
- A) Poner las reglas en `CLAUDE.md` raíz.
- B) Crear un `CLAUDE.md` en cada subdirectorio que contenga tests.
- C) **Crear `.claude/rules/testing.md` con `paths: ["**/*.test.ts"]`** para carga condicional.
- D) Incluir las reglas en `~/.claude/CLAUDE.md`.

**Respuesta:** **C**. Es exactamente el caso de uso de path-specific rules: convención que aplica a archivos dispersos, sin inflar el contexto cuando no se tocan. **B** funciona pero duplica trabajo; **A** infla el contexto en todas las sesiones; **D** sólo aplica a tu usuario.
