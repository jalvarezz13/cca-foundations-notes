# 3.4 — Plan mode vs ejecución directa

> **Dominio 3 — Claude Code Configuration & Workflows · 20% del examen**

---

## 🎯 Concepto clave

**Plan mode** restringe al agente a **tools de sólo lectura** (Read, Grep, Glob, navegación) y le obliga a **proponer un plan** antes de tocar archivos. Es ideal para cambios grandes, exploración segura, o cuando hay múltiples enfoques posibles. **Ejecución directa** es el modo normal: el agente lee, planifica y aplica en el mismo turno. Usa plan mode para **comprometerse a un diseño antes de implementar**.

---

## 📚 Profundización

### Cómo entrar en plan mode

| Vía | Cómo |
|---|---|
| Interactivo | `/plan` o `Shift+Tab` |
| CLI | `--permission-mode plan` |
| Por sesión | Configurable en el perfil de sesión |

### Qué se permite y qué no

| Tool | En plan mode |
|---|---|
| `Read` | ✅ |
| `Grep` | ✅ |
| `Glob` | ✅ |
| `Bash` (read-only: `ls`, `git status`, `cat`) | ✅ |
| `Bash` (con efectos: `npm install`, `git push`) | ❌ bloqueado |
| `Write` | ❌ bloqueado |
| `Edit` | ❌ bloqueado |
| `WebFetch` / `WebSearch` | ✅ (lectura) |

### Output esperado en plan mode

El agente debe producir un **plan estructurado**, no edits:

```markdown
## Plan

### Archivos a modificar
1. `src/auth/jwt.ts` — añadir refresh token logic.
2. `src/api/routes/auth.ts` — nuevo endpoint `/refresh`.
3. `tests/auth.test.ts` — añadir 3 tests.

### Pasos
1. Definir tipo `RefreshTokenPayload` en `jwt.ts`.
2. Implementar `generateRefreshToken()` y `verifyRefreshToken()`.
3. Añadir endpoint POST `/refresh` que toma cookie httpOnly.
4. Tests: caso happy path, token expirado, token inválido.

### Riesgos
- Compat con clientes antiguos: el cookie debe coexistir con el header bearer existente.
- DB migration NO necesaria (no se persisten refresh tokens en v1).

### Estimación
- 3 archivos modificados, ~80 líneas. Tests +50 líneas.
```

Una vez aprobado, sales de plan mode y ejecutas.

### Cuándo usar plan mode

- **Cambios grandes**: multi-archivo, multi-módulo, multi-PR.
- **Múltiples enfoques válidos**: refactor incremental vs rewrite, librería A vs B.
- **Decisiones arquitectónicas**: capas, contratos, naming.
- **Tareas donde el coste de equivocarse es alto**: schemas, migraciones, APIs públicas.
- **Codebases desconocidas**: el agente necesita explorar antes de comprometerse.

### Cuándo NO usar plan mode

- **Cambios simples**: rename, typo, una línea, un test.
- **Tareas donde tú ya sabes exactamente qué hacer**.
- **Iteraciones rápidas** (refinamiento de un ejemplo).

### Patrón "explore-then-execute"

```
1. Plan mode (read-only exploration)
   → produce plan + tradeoffs
2. Tú revisas / ajustas el plan
3. Salir de plan mode
4. Ejecutar el plan (Write/Edit)
```

### Combinar con subagente explore

Para exploración de codebases muy grandes:

```
Coordinator (plan mode)
  ↓
  task → explore subagent (sin contexto, sólo tools de lectura)
       → devuelve resumen estructurado al coordinator
  ↓
Plan basado en el resumen, sin inflar contexto del coordinator
```

> El **explore subagent** es ideal para encapsular discovery verboso. Devuelve sólo lo relevante.

### Plan mode + ejecución directa: combo

Patrón común:
1. **Plan mode** para investigar **un PR ajeno** (no quiero tocar nada): leo, analizo, formulo opinión.
2. **Ejecución directa** después para aplicar mi propio cambio basado en el aprendizaje.

---

## ⚠️ Anti-patrones

### 🔴 Plan mode para cambios triviales
Cambiar un literal de `3000` a `process.env.PORT || 3000` no necesita plan. Sobre-proceso.

### 🔴 No salir de plan mode tras aprobar
Quedas atascado leyendo sin poder ejecutar. Sal con la misma combinación (`/plan` toggle o nueva sesión sin `--permission-mode plan`).

### 🔴 Pedir plan, ignorarlo y dejar al agente improvisar
Pierde el valor: plan mode existe para forzar diseño antes de tocar.

### 🔴 Usar plan mode con tools destructivas como "lecturas"
`git push` no es lectura. `npm install` tampoco. Plan mode bloquea estas correctamente — no intentes saltártelas.

### 🔴 Plan demasiado breve / sin contexto
"Voy a editar 3 archivos." → no es plan. Falta qué, por qué, cómo, riesgos.

## ✅ Patrón correcto

### Plan mode para refactor multi-archivo

```bash
# Entrar a Claude Code en plan mode
claude --permission-mode plan
```

Pedido del usuario:
> "Quiero migrar de `axios` a `fetch` nativo en toda la app."

Output esperado del agente (en plan mode):

```markdown
## Plan: Migrate axios → fetch

### Inventario
- 14 archivos en `src/` importan `axios`.
- 3 patrones distintos de uso: GET con headers, POST con body JSON, requests con `axios.create()`.

### Decisiones
- Crear `src/lib/http.ts` con wrapper sobre `fetch` para mantener API similar.
- Conservar tipado con un genérico `<T>` para la response.
- Tests con `msw` (ya en uso) para mock.

### Fases
1. Crear `src/lib/http.ts` con `get`, `post`, `put`, `delete`.
2. Reemplazar usos de `axios.get(url)` → `http.get(url)`.
3. Eliminar import de `axios` y `package.json` dep.
4. Tests E2E para los flujos críticos.

### Riesgos
- Diferencias en manejo de errores: `axios` lanza en !2xx, `fetch` no. El wrapper lo normaliza.
- Interceptors de axios → equivalentes vía middleware en `http.ts`.

### Estimación
- 14 archivos, ~60 líneas modificadas + 80 líneas nuevas en `http.ts`.

¿Procedo a implementar?
```

Usuario aprueba → sale de plan mode → ejecuta.

### Plan mode + explore subagent para exploración profunda

```python
# Coordinador en plan mode
# Para un repo desconocido grande, delegar exploración a subagente

task(
    subagent_type="explore",
    prompt="""
    Analyze the codebase architecture: layers, dependency direction, where domain logic lives, where infrastructure lives. Return a 1-page summary with file paths.
    """,
)

# Subagente vuelve con summary
# Coordinator usa summary para hacer el plan
```

## 🧪 Escenario de examen

**Pregunta tipo:** "Un equipo quiere que Claude proponga un plan completo antes de tocar archivos en cambios grandes y multi-módulo. ¿Mejor configuración?"

**Opciones:**
- A) Añadir al system prompt "Always propose a plan first".
- B) **Usar plan mode (`/plan` interactivo o `--permission-mode plan` en CLI)**, que restringe tools destructivas y obliga al agente a producir un plan estructurado.
- C) Bloquear `Write` y `Edit` con un hook.
- D) Pedir al usuario que envíe el cambio por chunks.

**Respuesta:** **B**. Plan mode es la primitiva diseñada para esto: restringe físicamente las tools peligrosas y promueve el plan. **A** es probabilístico (~95%). **C** funciona pero es manual y ad-hoc.
