# 3.5 — Refinamiento iterativo

> **Dominio 3 — Claude Code Configuration & Workflows · 20% del examen**

---

## 🎯 Concepto clave

La mejor forma de mejorar resultados con Claude es **iterar con ejemplos concretos**, no afinar instrucciones en prosa. Tres técnicas canónicas: (1) compartir ejemplos input/output **del propio codebase**, (2) **test-driven iteration** — escribir tests primero e iterar compartiendo fallos, (3) patrón **interview** — pedirle al agente que haga preguntas antes de implementar. Issues interconectados → un solo mensaje; issues independientes → mensajes separados.

---

## 📚 Profundización

### Ejemplos concretos > descripciones vagas

🔴 **Vago:**
```
"Asegúrate de que el código sea limpio y siga buenas prácticas."
```
→ "Limpio" es subjetivo. El modelo aplica un promedio que puede no coincidir con tu equipo.

🟢 **Concreto:**
```
"Sigue el estilo de src/auth/jwt.ts:
- Imports agrupados (libs externas, módulos internos, tipos).
- Funciones pequeñas, una por export.
- Tests al lado del archivo (foo.ts + foo.test.ts).
- JSDoc con @example en las funciones públicas."
```
Mejor todavía: pegar el archivo de referencia o enviar su path.

### Test-driven iteration

Patrón:
```
1. Pides al agente: "Escribe los tests para la función X que aún no existe."
2. Tests escritos, falla al correrlos.
3. Pides: "Implementa la función X para que pasen estos tests".
4. Si fallan tests específicos, pegas el output del runner.
5. Iteras compartiendo el output del test.
```

Ventajas:
- Los tests son **criterios de aceptación verificables**.
- El feedback loop es el output del test runner, no tu juicio subjetivo.
- Te da regression suite automática.

### Patrón "interview" — preguntas antes de implementar

```
Usuario: "Implementa un sistema de notificaciones."
Agente (modo interview): "Antes de implementar, necesito clarificar:
1. ¿Canales? (email, push, in-app, todos)
2. ¿Persistencia? (DB, queue, fire-and-forget)
3. ¿Retry policy?
4. ¿Templates parametrizables o hardcoded?
5. ¿Multilenguaje?

¿Puedes responder a 1-5 antes de que empiece?"
```

Cómo inducirlo:
```
system_prompt = """
Before implementing, ask clarifying questions if the spec is incomplete.
Only proceed once requirements are explicit.
"""
```

O simplemente, en el user message:
> "Before writing code, ask me anything you need to clarify."

### Issues interconectados en UN solo mensaje

> Cuando los problemas comparten contexto, pegarlos juntos da al modelo **visión global**.

Ejemplo: dos bugs en un mismo módulo. Mejor:
```
"Hay dos issues en src/billing:
1. el cálculo de IVA no aplica al envío.
2. el descuento se aplica antes del IVA en lugar de después.
¿Puedes proponer fix coherente para ambos?"
```

→ El agente puede ver que ambos tocan la función `computeTotal()` y proponer un fix conjunto.

Si los envías por separado, el segundo puede romper el primero.

### Issues independientes en mensajes separados

Si dos issues están en módulos **no relacionados**, separa: mejor focus, mejor diff, menos riesgo de regresión cruzada.

```
Mensaje 1: "Bug en auth: el JWT expira a los 5 min cuando debería a las 24h."
Mensaje 2: "UI: el botón de logout no aparece en móvil."
```

### Refinamiento sobre el output del agente

Si el primer intento es 80% bueno:
```
"Está bien, pero:
- línea 12: usa `Date.now()` en lugar de `new Date().getTime()`.
- línea 24: cubre el caso de array vacío.
Aplica esos cambios."
```

> **Específico por línea > vago general.** "Mejóralo" es ambigüo. "Cambia X a Y en la línea N" es ejecutable.

### Few-shot del propio codebase

```
"Sigue el patrón de src/api/users.ts para implementar src/api/products.ts:
- Misma estructura de imports.
- Mismos middlewares (auth, rate-limit, logging).
- Mismos error handlers.
- Tests con la misma forma."
```

Pegar (o referenciar con file link) el archivo template **funciona mejor** que cualquier prosa explicando "follow the established conventions."

## ⚠️ Anti-patrones

### 🔴 Instrucciones vagas
"Hazlo limpio", "buena calidad", "best practices" → el modelo interpola con su prior, que puede no coincidir con tu codebase.

### 🔴 Stack overflow de tweaks
Enviar 5 mensajes en cadena cada uno cambiando un detalle → el contexto se llena de iteraciones, el agente pierde foco. Mejor: agrupa los tweaks en un mensaje.

### 🔴 Sin tests ni criterios verificables
Si no hay forma de saber cuándo está bien, las iteraciones son interminables. Define criterio antes (test, ejemplo, schema).

### 🔴 No usar el patrón interview ante ambigüedad
Implementar a ciegas cuando el spec es ambiguo produce trabajo que hay que tirar. Pregunta primero.

### 🔴 Issues no relacionados juntos
Mezclar bug en auth con feature de UI → agente se distrae, diff inmanejable, PR difícil de revisar.

### 🔴 Pegar el output del test sin más contexto
Pegar `FAIL test/foo.test.ts` sin el detalle del error no ayuda. Pega el error completo + stack.

## ✅ Patrón correcto

### Iteración test-driven

```
USUARIO: "Quiero una función parseInvoiceTotal(rawText: string) que extraiga el total
de una factura en texto plano. Empezamos por los tests."

CLAUDE: [Escribe tests cubriendo: total con símbolo €, sin símbolo, con coma decimal,
con miles, factura sin total → error claro]

USUARIO: "Vale, ahora implementa parseInvoiceTotal para que pasen."

CLAUDE: [implementa]

USUARIO (ejecuta tests, ve fail):
"El test 'extracts total with comma decimal' falla:
  Expected 1234.56
  Received 1234
La factura ejemplo dice '1.234,56€' (formato europeo)."

CLAUDE: [ajusta el parser para soportar punto como separador de miles + coma como decimal]
```

### Iteración interview

```
USUARIO: "Necesito un sistema de export de datos del usuario."

CLAUDE: "Antes de implementar, clarifica:
1. Formato(s): CSV, JSON, PDF, otros?
2. Scope: sólo tabla users o también orders, invoices, etc.?
3. Async (job + email con link) o sync (download inmediato)?
4. Compliance: GDPR export incluye logs y metadata?
5. Tamaño esperado: <10MB o gigabytes?"

USUARIO: "1. JSON y CSV. 2. users + orders + invoices. 3. Async porque puede ser
grande. 4. Sí, GDPR completo. 5. Hasta 500MB en algunos casos."

CLAUDE: [propone arquitectura con job queue, streaming, signed URLs]
```

## 🧪 Escenario de examen

**Pregunta tipo:** "Un developer pasa horas iterando en prompts vagos como 'hazlo más limpio'. El resultado fluctúa entre intentos. ¿Mejor enfoque?"

**Opciones:**
- A) Usar un modelo más grande.
- B) Subir el `max_tokens`.
- C) **Compartir ejemplos concretos del propio codebase (file path o pega) y criterios verificables (tests, schemas, linter output) en vez de descripciones en prosa.**
- D) Pedir al modelo que sea más conservador.

**Respuesta:** **C**. La causa raíz es la ambigüedad del criterio. Ejemplos concretos + criterios verificables (tests, schemas) eliminan la fluctuación. **D** ("be conservative") no mejora precisión real.
