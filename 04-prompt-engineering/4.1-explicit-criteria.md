# 4.1 — Prompts con criterios explícitos

> **Dominio 4 — Prompt Engineering & Structured Output · 20% del examen**

---

## 🎯 Concepto clave

**Criterios concretos > instrucciones vagas.** Decir "flag cuando el comentario contradice el código" da resultados consistentes; "verifica que los comentarios sean precisos" no. Y las muletillas tipo "be conservative" o "only high-confidence" **NO mejoran precisión real** — sólo reducen el número de outputs (escondiendo el problema). El examen castiga las opciones que confían en estas muletillas.

---

## 📚 Profundización

### Vagos vs específicos — ejemplos lado a lado

🔴 **Vago:**
```
"Verifica que los comentarios del código sean precisos."
```
**Problema:** "precisos" es ambiguo. ¿Quiere decir gramática? ¿Significado? ¿Que coincide con el código?

🟢 **Específico:**
```
"Para cada comentario en el archivo:
- Si el comentario describe el comportamiento del bloque siguiente:
  - flag si el comentario CONTRADICE el código (ej. dice "returns null on error" pero el código lanza).
  - flag si el comentario describe un comportamiento OBSOLETO (referencia variable que ya no existe).
- NO flagear comentarios sobre 'por qué' (intención de diseño) — no son verificables contra el código.
- NO flagear typos ortográficos.
- Severidad: HIGH si el comentario afecta seguridad/correctness; MEDIUM si confunde uso; LOW si es trivial."
```

→ El segundo prompt:
- Lista qué SÍ flagear y qué NO.
- Define severidad con criterio operativo.
- Excluye explícitamente categorías ambiguas.

### Muletillas que NO funcionan

Frases comunes que **suenan** prudentes pero **no mejoran precisión**:

- "Be conservative"
- "Only flag high-confidence issues"
- "If in doubt, don't report"
- "Use your best judgment"
- "Only report clear bugs"

> **Por qué no funcionan:** son apelaciones genéricas, no criterios verificables. El modelo aplica un threshold subjetivo distinto cada vez. **No es que se vuelva más preciso — es que se vuelve más callado.** Pasas de falsos positivos a falsos negativos.

**La solución correcta:** describir el threshold con ejemplos de qué SÍ es un issue y qué NO.

### Falsos positivos minan la confianza del developer

Si un bot de code review reporta 80 issues por PR de los que sólo 20 son reales, el developer empieza a ignorar TODOS los comentarios, incluyendo los 20 reales. **Coste asimétrico.**

Estrategias para reducir falsos positivos:

1. **Few-shot con contraste**: ejemplo de `bug real` + ejemplo de `pattern aceptable que parece bug`.
2. **Excluir explícitamente** patrones comunes que no son bugs en tu codebase.
3. **Verificación posterior**: pipeline donde una instancia detecta y otra verifica.
4. **Criterio de severidad** con ejemplos por nivel.

### Severidad con ejemplos concretos

```
Severity levels:

HIGH (impacts security or correctness):
  Examples:
  - SQL query built by string concatenation with user input (SQL injection).
  - Token stored in localStorage (XSS-readable).
  - Off-by-one in a loop reading user data (data leak).

MEDIUM (potential bug, edge case mishandled):
  Examples:
  - `array[0]` without checking emptiness.
  - Catch block that swallows error without logging.
  - Missing await on async function call.

LOW (style, maintainability):
  Examples:
  - Magic number (replace with named const).
  - Function >50 lines (consider extracting).
  - Inconsistent naming (camelCase vs snake_case in same file).
```

> Anthropic documenta este patrón: dar al modelo **ejemplos** por nivel de severidad funciona mejor que adjetivos.

### Cobertura primero, filtrado después

> Para code review, el patrón oficial es "Report every issue you find, including ones you are uncertain about" — luego se filtra/clasifica.

```
Pass 1 (cobertura): "Report every issue you find. Don't filter by confidence."
Pass 2 (clasificación): "Given these issues, assign severity and filter the false positives."
```

Razón: si pides "be conservative" en el pass 1, el modelo **descarta** issues que un humano sí querría ver. Mejor: pásalos todos, **luego** filtra con criterio explícito.

## ⚠️ Anti-patrones

### 🔴 "Be conservative" como técnica de precisión
No funciona. Convierte falsos positivos en falsos negativos.

### 🔴 "Be thorough" sin definir thorough
"Be thorough" es tan vago como "be careful". Define qué cubrir explícitamente.

### 🔴 Severidad sin ejemplos
"low/medium/high" sin definir cada nivel → el modelo asigna inconsistente.

### 🔴 Pedir "use your best judgment"
Transfiere el problema sin resolverlo. Define el judgment con criterios.

### 🔴 Criterio escondido en el system prompt
Si las reglas viven en el system prompt y se contradicen con el user prompt, el modelo se confunde.

### 🔴 No incluir negativos
Sin "NO flagear" ejemplos, el modelo flagea defensivamente todo.

## ✅ Patrón correcto

### Prompt de code review con criterios operativos

```
You are reviewing a JavaScript/TypeScript pull request. For each issue:

OUTPUT: {file, line, severity, category, message, suggested_fix}

SEVERITY:
- HIGH: security vuln, data corruption, crash. Examples:
  * SQL/NoSQL injection.
  * Reading env in client-side bundle.
  * Race condition on shared state.
- MEDIUM: likely bug or risky pattern. Examples:
  * Missing await on async function.
  * Unbounded recursion.
  * Mutation of function argument.
- LOW: style or maintainability. Examples:
  * Function >100 lines.
  * Magic number.

CATEGORY: security | correctness | performance | style | maintainability

DO flag:
- Comment that contradicts the code below it.
- Function that returns inconsistent types depending on path.
- Missing error handling for async operations.

DO NOT flag:
- TODO/FIXME comments.
- Disabled lint rules with inline justification.
- Tests using `any` for mocking purposes.
- Type assertions in conversion utilities.
```

### Verbalización del criterio en few-shot

```
EXAMPLE 1 — flag this:
  code:   `const id = req.query.userId; db.query("SELECT * FROM u WHERE id=" + id)`
  finding: {severity: HIGH, category: security, message: "SQL injection: query built via concatenation."}

EXAMPLE 2 — DO NOT flag this (aceptable in this codebase):
  code:   `const id = req.query.userId; db.query("SELECT * FROM u WHERE id=$1", [id])`
  reason: parameterized query, safe.

EXAMPLE 3 — flag this:
  code:   `/* returns null on error */
           function load() { throw new Error('fail'); }`
  finding: {severity: MEDIUM, category: correctness, message: "Comment says 'returns null on error' but function throws."}
```

## 🧪 Escenario de examen

**Pregunta tipo:** "Un bot de code review usa prompt: 'Be conservative and only flag high-confidence bugs.' El equipo nota que pasa por alto issues importantes. ¿Mejor solución?"

**Opciones:**
- A) Cambiar a 'be aggressive'.
- B) **Reemplazar 'be conservative' con criterios específicos: qué patrones flagear, qué NO flagear, y ejemplos por nivel de severidad.**
- C) Subir el modelo.
- D) Reducir `max_tokens` para forzar respuestas más cortas.

**Respuesta:** **B**. "Be conservative" no es un criterio, es una apelación vaga. Convertirlo en reglas concretas con ejemplos elimina la fluctuación y mejora detección sin inflar falsos positivos.
