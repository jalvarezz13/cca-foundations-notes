# 4.2 — Few-shot prompting

> **Dominio 4 — Prompt Engineering & Structured Output · 20% del examen**

---

## 🎯 Concepto clave

**Few-shot prompting** — incluir **2-5 ejemplos** de input/output dentro del prompt — es **una de las técnicas más fiables** para controlar formato, tono, estructura y reducir falsos positivos. Es **más efectiva que** instrucciones detalladas en prosa cuando hay ambigüedad. Anthropic recomienda **3-5 ejemplos** envueltos en tags `<example>...</example>` o `<examples>...</examples>`.

---

## 📚 Profundización

### Por qué few-shot supera a las instrucciones

Tres razones:

1. **Concreto vence a abstracto.** Una instrucción ("incluye severity") deja margen de interpretación. Un ejemplo (`severity: "HIGH"`) lo elimina.
2. **Patrón observable.** El modelo es excelente generalizando desde ejemplos. Aprende el formato y los criterios implícitos a la vez.
3. **Ancla el formato.** El JSON exacto, el orden de campos, el tono — todo se transfiere.

### Cuántos ejemplos

| Nº ejemplos | Efecto |
|---|---|
| 0 (zero-shot) | Sólo instrucciones. Buen baseline si la tarea es estándar. |
| 1 (one-shot) | Útil para mostrar formato; insuficiente para casos ambiguos. |
| **3-5** | **Sweet spot oficial.** Cubre variaciones y casos edge. |
| 6+ | Diminishing returns. Infla el prompt sin mejorar accuracy. |

> El examen acepta tanto **2-4** (rango aceptable en muchos escenarios) como **3-5** (rango oficial documentado). Lo importante es **no menos de 2** y **no más de ~6**.

### Estructura recomendada con XML

Anthropic recomienda envolver ejemplos:

```
<examples>

<example>
<input>
"I want my money back, this is ridiculous!!!"
</input>
<output>
{"sentiment": "negative", "intent": "refund_request", "urgency": "high"}
</output>
</example>

<example>
<input>
"Quick question — when does the spring sale end?"
</input>
<output>
{"sentiment": "neutral", "intent": "inquiry", "urgency": "low"}
</output>
</example>

<example>
<input>
"Got my order, love it. Thanks!"
</input>
<output>
{"sentiment": "positive", "intent": "compliment", "urgency": "low"}
</output>
</example>

</examples>
```

### Ejemplos con razonamiento (`<thinking>`)

Para clasificación compleja, mostrar el razonamiento ayuda:

```xml
<example>
<input>The product arrived broken but support replaced it quickly.</input>
<thinking>
- Negative element: "arrived broken".
- Positive element: "support replaced it quickly".
- Net sentiment: mixed but with positive resolution → label = mixed_positive.
- Intent: it's a review, not a request.
</thinking>
<output>
{"sentiment": "mixed_positive", "intent": "review"}
</output>
</example>
```

> El modelo aprende **cómo** llegar al label, no sólo el label. Reduce errores en casos similares.

### Distinguir patrones aceptables de issues reales

> Para review, **incluir ejemplos negativos** (lo que parece bug pero NO lo es) reduce falsos positivos drásticamente.

```xml
<example label="DO_NOT_FLAG — accepted pattern in this codebase">
<code>db.query("SELECT * FROM users WHERE id = $1", [userId])</code>
<reason>Parameterized query. Safe. We use $N placeholders intentionally.</reason>
</example>

<example label="FLAG — real injection risk">
<code>db.query("SELECT * FROM users WHERE id = " + userId)</code>
<reason>String concatenation with unsanitized input.</reason>
</example>
```

### Extracción de documentos con formatos variados

Few-shot brilla en extracción cuando los documentos vienen en formatos heterogéneos (PDFs de distintos proveedores, emails de distintos clientes). Ejemplos cubren cada variante:

```xml
<example>
<input>Invoice format A (US, USD, MM/DD/YYYY)</input>
<output>{"date": "2024-11-12", "total": 1234.56, "currency": "USD"}</output>
</example>

<example>
<input>Invoice format B (EU, EUR, DD.MM.YYYY, decimal coma)</input>
<output>{"date": "2024-11-12", "total": 1234.56, "currency": "EUR"}</output>
</example>

<example>
<input>Invoice format C (handwritten notes scanned, partial data)</input>
<output>{"date": "2024-11-12", "total": 1234.56, "currency": null, "notes": "currency unclear, request confirmation"}</output>
</example>
```

### Demostrar el formato deseado

Si quieres output `{location, issue, severity, suggested_fix}`, no lo describes en prosa — pones ejemplos con ese formato exacto:

```xml
<example>
<output>
{
  "location": "src/auth.ts:42",
  "issue": "JWT secret read from process.env on every request",
  "severity": "medium",
  "suggested_fix": "Cache the secret at module level: `const SECRET = process.env.JWT_SECRET`."
}
</output>
</example>
```

## ⚠️ Anti-patrones

### 🔴 Un solo ejemplo
Insuficiente para que el modelo generalice. Sweet spot 3-5.

### 🔴 Ejemplos contradictorios
Si dos ejemplos similares devuelven outputs diferentes sin razón, el modelo se rompe. Cohérencia obligatoria.

### 🔴 Ejemplos no representativos
Sólo casos triviales → el modelo falla en casos edge. Incluye **al menos uno difícil**.

### 🔴 Ejemplos demasiado largos
Cada ejemplo es contexto consumido. Si cada uno son 500 tokens y pones 5, son 2500 sólo en ejemplos. Resume cuando puedas.

### 🔴 Olvidar ejemplos negativos para reducir falsos positivos
Si sólo muestras "qué SÍ flagear", el modelo flagea todo. Incluye "qué NO flagear" explícito.

### 🔴 Few-shot sin tags ni delimitadores
Pegar ejemplos en prosa sin `<example>` o `Input/Output` → el modelo se confunde sobre dónde empieza/termina cada ejemplo.

### 🔴 Few-shot ignorando lo que ya está en el contexto
Si tu CLAUDE.md ya tiene 5 ejemplos del mismo patrón, no añadas otros 5 en el user message — duplicas.

## ✅ Patrón correcto

### Few-shot completo para clasificación de tickets

```python
prompt = """
You classify customer support tickets. Output JSON with: category, priority, sentiment.

Categories: refund | shipping | account | technical | other
Priority: P0 (severe loss) | P1 (urgent) | P2 (normal) | P3 (low)

<examples>

<example>
<input>"My card was charged twice for order #4892, please refund the duplicate."</input>
<output>{"category": "refund", "priority": "P1", "sentiment": "neutral"}</output>
</example>

<example>
<input>"WHERE IS MY ORDER??? I've waited 3 weeks!"</input>
<output>{"category": "shipping", "priority": "P1", "sentiment": "negative"}</output>
</example>

<example>
<input>"Hi, just wondering when the spring sale starts? Thanks!"</input>
<output>{"category": "other", "priority": "P3", "sentiment": "positive"}</output>
</example>

<example>
<input>"Site is completely down, can't checkout, losing sales every minute."</input>
<output>{"category": "technical", "priority": "P0", "sentiment": "negative"}</output>
</example>

</examples>

Now classify this ticket:
<input>{ticket}</input>
"""
```

### Few-shot con razonamiento para reducir falsos positivos en code review

```xml
<examples>

<example>
<code>
const id = req.query.userId;
db.query("SELECT * FROM users WHERE id = $1", [id]);
</code>
<thinking>
- Uses parameterized query with $1 placeholder.
- userId passed as parameter, not interpolated.
- Safe.
</thinking>
<output>NO_FLAG</output>
</example>

<example>
<code>
const id = req.query.userId;
db.query(`SELECT * FROM users WHERE id = ${id}`);
</code>
<thinking>
- Template literal with userId interpolation.
- userId comes from req.query (user input).
- This is SQL injection.
</thinking>
<output>FLAG severity=HIGH category=security message="SQL injection: user input interpolated into SQL string. Use parameterized query."</output>
</example>

</examples>
```

## 🧪 Escenario de examen

**Pregunta tipo:** "Un equipo intenta clasificar tickets de soporte. Con instrucciones detalladas en prosa, el modelo es inconsistente: para inputs similares devuelve categorías distintas en runs diferentes. ¿Mejor solución?"

**Opciones:**
- A) Reducir `temperature` a 0.
- B) Usar un modelo más grande.
- C) **Añadir 3-5 ejemplos few-shot que cubran las categorías y muestren cómo manejar casos ambiguos.**
- D) Pedir al modelo que sea "más consistente".

**Respuesta:** **C**. Para consistencia de clasificación con casos ambiguos, few-shot es la técnica canónica oficial. **A** reduce variabilidad pero no resuelve la ambigüedad del criterio. **D** es vaga e ineficaz.
