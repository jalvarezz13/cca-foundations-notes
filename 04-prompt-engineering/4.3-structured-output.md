# 4.3 — Output estructurado con tool use y JSON schemas

> **Dominio 4 — Prompt Engineering & Structured Output · 20% del examen**

---

## 🎯 Concepto clave

La forma **más fiable** de producir output estructurado en Claude es **tool use con JSON schema**: define una tool con `input_schema`, usa `tool_choice` para forzarla, y el SDK garantiza que el output cumple el schema sintácticamente. **OJO:** garantiza **conformidad de schema**, no **verdad semántica** — el modelo puede llenar campos con datos inconsistentes (líneas que no suman, fechas inventadas). Para corrección semántica hace falta verificación posterior o patrones de self-check.

---

## 📚 Profundización

### Patrón canónico: tool con schema + `tool_choice` forzado

```python
INVOICE_TOOL = {
    "name": "record_invoice",
    "description": "Records the extracted invoice data.",
    "input_schema": {
        "type": "object",
        "properties": {
            "invoice_number": {"type": "string"},
            "date": {"type": "string", "format": "date"},
            "vendor": {"type": "string"},
            "currency": {"type": "string", "enum": ["USD", "EUR", "GBP", "OTHER"]},
            "currency_other": {"type": ["string", "null"]},
            "line_items": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "description": {"type": "string"},
                        "quantity": {"type": "number"},
                        "unit_price": {"type": "number"},
                        "line_total": {"type": "number"}
                    },
                    "required": ["description", "unit_price", "line_total"]
                }
            },
            "stated_total": {"type": "number"},
            "calculated_total": {"type": "number"},
            "discrepancy": {"type": "boolean"}
        },
        "required": ["invoice_number", "date", "vendor", "currency", "line_items", "stated_total", "calculated_total", "discrepancy"]
    }
}

response = client.messages.create(
    model="claude-opus-4-5",
    messages=[{"role": "user", "content": f"Extract invoice data:\n\n{pdf_text}"}],
    tools=[INVOICE_TOOL],
    tool_choice={"type": "tool", "name": "record_invoice"},  # ← FUERZA esta tool
    max_tokens=2048,
)

# response.content[0].input es ahora el JSON validado contra el schema
data = response.content[0].input
```

> Con `tool_choice` forzado, el modelo **no responde en texto** — emite directamente el `tool_use` con `input` validado.

### Tres mecanismos para output estructurado

| Mecanismo | Comportamiento | Cuándo usar |
|---|---|---|
| Texto libre + parse | Pedir JSON en texto, parsear con `json.loads()` | NUNCA en producción. Frágil. |
| Tool use con `tool_choice` auto | Modelo decide si llamar tool | Conversación que A veces estructura |
| **Tool use con `tool_choice` forzado** | Modelo SIEMPRE devuelve el tool input | **Extracción / clasificación garantizada** |

### `tool_choice` recap

```python
tool_choice = "auto"                                    # modelo decide
tool_choice = "any"                                     # alguna tool sí o sí
tool_choice = {"type": "tool", "name": "record_invoice"}  # esa tool sí o sí
tool_choice = "none"                                    # nunca
```

### Schemas garantizan FORMA, no SEMÁNTICA

> Anthropic explícitamente documenta: structured outputs garantizan **conformidad de esquema**, NO verdad/factualidad.

Ejemplos de fallo semántico **dentro** del schema:

| Error | Schema lo permite | Solución |
|---|---|---|
| `line_items` que no suman el `stated_total` | Sí (campos independientes) | Campo `calculated_total` + check |
| `date: "1900-01-01"` cuando la fecha era ilegible | Sí (es una fecha válida) | `date_confidence: "low"` |
| `vendor: "Acme Corp"` inventado | Sí (string válido) | Citar fuente: `vendor_extracted_from_text: "..."` |
| `currency: "USD"` cuando era "GBP" | Sí (enum válido) | Few-shot con casos ambiguos |

### Patrones para reducir errores semánticos

🟢 **Nullable / optional para campos inciertos**
```json
{"currency": {"type": ["string", "null"], "enum": ["USD","EUR","GBP",null]}}
```
→ El modelo puede declarar "no sé" en lugar de fabricar.

🟢 **Enums extensibles con `unclear`/`other` + `detail`**
```json
{
  "category": {"type": "string", "enum": ["refund","shipping","account","other"]},
  "category_detail": {"type": ["string","null"]}
}
```
→ "other" + descripción evita forzar un encasillamiento erróneo.

🟢 **Self-check con `calculated_total` vs `stated_total`**
```json
{
  "stated_total": {"type": "number"},
  "calculated_total": {"type": "number"},
  "discrepancy": {"type": "boolean"}
}
```
→ El modelo calcula el total a partir de las líneas. Si difiere, marca `discrepancy: true`. Tú lo detectas en post-proceso.

🟢 **`conflict_detected` para fuentes inconsistentes**
```json
{
  "amount_cents": {"type": "integer"},
  "amount_source": {"type": "string"},
  "conflict_detected": {"type": "boolean"},
  "conflict_notes": {"type": ["string","null"]}
}
```
→ Si dos lugares del documento dan amounts distintos, marca el conflicto.

🟢 **Confidence per-field**
```json
{
  "vendor": {"type": "string"},
  "vendor_confidence": {"type": "string", "enum": ["high","medium","low"]}
}
```
→ Routing a humano para confidence bajo.

### Compat con extended thinking

> Con **extended thinking** activado, `tool_choice = "any"` y `tool_choice = {"type":"tool",...}` **no son compatibles**. Sólo `"auto"` y `"none"`.

Si necesitas extracción estructurada con extended thinking → diseña el prompt para que el modelo elija `auto` la tool, y verifica que la elija (si no, retry con instrucción más explícita).

## ⚠️ Anti-patrones

### 🔴 Pedir JSON en texto libre
```
"Output JSON: {...}"
```
→ Frágil. Errores de sintaxis (comas, comillas), valores escapeados mal. **Usa tool use.**

### 🔴 Schema strict permisivo
```json
{"properties": {...}}  // sin "required"
```
→ El modelo omite campos. Usa `required` exhaustivo.

### 🔴 Schemas con campos demasiado abiertos cuando hay enums viables
```json
{"category": {"type": "string"}}  // ❌ accepta cualquier cosa
```
→ Usa enum.

### 🔴 No incluir `null` ni `"unclear"` en campos inciertos
→ El modelo **fabrica** un valor antes que dejarlo en blanco.

### 🔴 Confiar en que el schema previene errores semánticos
El schema garantiza forma. Los errores semánticos (línea que no suma, fecha mal interpretada) **siguen siendo posibles**. Diseña self-checks.

### 🔴 `tool_choice = "any"` con extended thinking
No compatible. Falla la request.

## ✅ Patrón correcto

### Extractor de facturas con self-check completo

```python
INVOICE_TOOL = {
    "name": "record_invoice",
    "description": "Records the extracted invoice fields with confidence and reconciliation.",
    "input_schema": {
        "type": "object",
        "properties": {
            "invoice_number": {"type": "string"},
            "invoice_number_confidence": {"type": "string", "enum": ["high","medium","low"]},

            "date": {"type": ["string","null"], "format": "date"},
            "date_confidence": {"type": "string", "enum": ["high","medium","low","not_found"]},

            "vendor": {"type": "string"},

            "currency": {"type": "string", "enum": ["USD","EUR","GBP","JPY","OTHER"]},
            "currency_other": {"type": ["string","null"]},

            "line_items": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "description": {"type": "string"},
                        "quantity": {"type": "number"},
                        "unit_price": {"type": "number"},
                        "line_total": {"type": "number"}
                    },
                    "required": ["description","unit_price","line_total"]
                }
            },

            "stated_total": {"type": "number"},
            "calculated_total": {"type": "number"},
            "discrepancy": {"type": "boolean"},
            "discrepancy_amount": {"type": ["number","null"]},

            "issues": {
                "type": "array",
                "items": {
                    "type": "string",
                    "enum": ["partial_data","handwritten","damaged","multiple_currencies","unclear_total"]
                }
            }
        },
        "required": ["invoice_number","date_confidence","vendor","currency","line_items","stated_total","calculated_total","discrepancy"]
    }
}

response = client.messages.create(
    model="claude-opus-4-5",
    tools=[INVOICE_TOOL],
    tool_choice={"type": "tool", "name": "record_invoice"},
    messages=[{"role": "user", "content": f"Extract invoice data. For each numeric field, also output a confidence level. Compute calculated_total from line_items and compare with the stated total.\n\n{pdf_text}"}],
)

data = response.content[0].input

# Post-proceso: routing
if data["discrepancy"] or data["date_confidence"] == "low" or "unclear_total" in data.get("issues", []):
    route_to_human(data)
else:
    auto_process(data)
```

## 🧪 Escenario de examen

**Pregunta tipo:** "Un pipeline extrae datos de facturas en JSON. El equipo verifica que el JSON SIEMPRE es sintácticamente válido (cumple schema), pero ~5% de los outputs tienen `line_items` cuyas sumas no coinciden con el `total`. ¿Mejor solución?"

**Opciones:**
- A) Hacer el schema más estricto.
- B) Subir el modelo.
- C) **Añadir campos `calculated_total` y `discrepancy` al schema; el modelo calcula el total desde las líneas y marca discrepancia. Detectar `discrepancy: true` en post-proceso y rutear a humano.**
- D) Pedir en el prompt "haz que los totales coincidan".

**Respuesta:** **C**. El error es semántico (sumas mal), no sintáctico — el schema no lo puede prevenir. Pero un campo de self-check en el schema lo expone para que el sistema lo detecte. **D** no funciona: pedir "que cuadren" induce al modelo a **modificar** los números para que cuadren (peor).
