# 4.4 — Validación, retry y feedback loops

> **Dominio 4 — Prompt Engineering & Structured Output · 20% del examen**

---

## 🎯 Concepto clave

Cuando un output no cumple criterios, **retry con error feedback** (incluir los errores de validación en el siguiente prompt) es la técnica oficial documentada. Pero **el retry no es mágico**: si la información no está en la fuente, ningún retry la generará — la respuesta correcta es **"insufficient data"**, no inventar. Anthropic documenta el patrón **draft → review → refine** (self-correction) y la regla **"retract claims you can't cite"** para reducir alucinaciones.

---

## 📚 Profundización

### Retry con error feedback

Patrón:

```python
def extract_with_retry(pdf_text, max_retries=3):
    history = [{"role": "user", "content": f"Extract invoice data:\n\n{pdf_text}"}]

    for attempt in range(max_retries):
        response = client.messages.create(
            model="claude-opus-4-5",
            tools=[INVOICE_TOOL],
            tool_choice={"type": "tool", "name": "record_invoice"},
            messages=history,
            max_tokens=2048,
        )
        data = response.content[0].input

        # Validación
        errors = validate(data)
        if not errors:
            return data

        # Retry: añadir errores al historial
        history.append({"role": "assistant", "content": response.content})
        history.append({"role": "user", "content": [
            {
                "type": "tool_result",
                "tool_use_id": response.content[0].id,
                "content": f"Validation errors:\n{format_errors(errors)}\n\nPlease re-extract correctly.",
                "is_error": True,
            }
        ]})

    raise RetryExhausted("Could not extract after 3 attempts.")


def validate(data):
    errors = []
    if data["stated_total"] != data["calculated_total"] and not data["discrepancy"]:
        errors.append("calculated_total mismatches stated_total but discrepancy=false.")
    if data["currency"] == "OTHER" and not data["currency_other"]:
        errors.append("currency=OTHER requires currency_other.")
    return errors
```

> Anthropic documenta que con retry se puede "reliably match complex schemas... especially if implemented with retries."

### Cuándo retry NO funciona

Casos donde retry es **inútil**:

1. **La info no está en la fuente.** Si la factura no tiene fecha, ningún retry hará que aparezca. La respuesta correcta es `date: null, date_confidence: "not_found"`.
2. **Información ambigua que requiere clarificación humana.** El modelo no puede preguntar al usuario en medio de un batch.
3. **Errores de modelo fundamentales** (limitación de capacidad). Retry no escala IQ.

> Si retry no funciona, el patrón es **route to human review** con el contexto del fallo (ver Dominio 5.5).

### Reglas oficiales sobre alucinaciones

Anthropic documenta dos reglas clave:

> "If it can't find a quote, **it must retract the claim**."

> "If you can't find relevant quotes, **state 'No relevant quotes found.'**"

→ **Mejor decir "no encontré" que fabricar.** Esto se enseña vía prompt:

```
For each claim in your answer, you must cite a quote from the sources.
If you cannot find a supporting quote for a claim, RETRACT the claim and say so explicitly.
Never include unsupported claims.
```

### Self-correction: draft → review → refine

Patrón oficial para mejorar precisión sin verificador externo:

```
1. DRAFT: "Write a first draft answering the question."
2. REVIEW: "Now review your draft against these criteria: [list]. Identify weaknesses."
3. REFINE: "Now write the final answer addressing the weaknesses you found."
```

Implementable en un solo prompt (con secciones) o en 3 turnos. Útil cuando no tienes un validador automatizado.

### Campos para análisis de descartes

Para entender por qué un sistema descarta findings (filtro post-detección), añade campos al schema:

```json
{
  "finding": "...",
  "detected_pattern": "regex_match_v2",
  "detected_confidence": "high",
  "filter_applied": "false_positive_check",
  "filter_decision": "kept"
}
```

→ Analizando los `filter_decision: "dropped"` ves qué patrones generan ruido y refinas el filtro.

### Self-check via campos en el schema

(Ya visto en 4.3, repaso operativo):

| Patrón | Campos | Detección |
|---|---|---|
| Reconciliación numérica | `stated_total`, `calculated_total`, `discrepancy` | `discrepancy: true` |
| Inconsistencia de fuentes | `value`, `source_a_value`, `source_b_value`, `conflict_detected` | `conflict_detected: true` |
| Confidence per-field | `field`, `field_confidence` | `field_confidence: "low"` |
| Origen de extracción | `field`, `field_excerpt` (texto fuente) | post-validación contra el documento |

### Validador determinista en post-proceso

Tras el output del modelo, **un validador en código** debería:

- Tipos correctos.
- Reglas de negocio (`amount > 0`, fechas razonables).
- Cross-checks (suma de líneas vs total).
- Patrones conocidos de fabricación (vendor en lista de proveedores reales, etc.).

El validador devuelve errores estructurados que alimentan el retry.

## ⚠️ Anti-patrones

### 🔴 Retry sin pasar los errores específicos
```
"It didn't work, try again."  ❌
```
El modelo no sabe **qué** falló. Pasa los errores literales.

### 🔴 Retry infinito
Sin `max_retries`, gastas tokens infinitos en casos imposibles. 3 retries es razonable.

### 🔴 Retry cuando la info no está
Si no hay fecha en el documento, retry no la inventa. Acepta `date: null`.

### 🔴 Fabricar para "rellenar"
Pedir "haz que cuadren los totales" → el modelo modifica las líneas para que sumen al total declarado, fabricando datos. **Patrón tóxico.**

### 🔴 No incluir mecanismo de "I don't know"
Si tu schema requiere `vendor` siempre, el modelo fabrica. Permite `vendor: null` o `vendor_confidence: "not_found"`.

### 🔴 Self-correction sin criterios concretos
"Review your answer" → vago. "Review against [lista de criterios concretos]" → útil.

## ✅ Patrón correcto

### Extractor con retry, validación y fallback a human review

```python
def extract_invoice(pdf_text):
    history = [{"role": "user", "content": _build_extract_prompt(pdf_text)}]

    for attempt in range(3):
        data = _call_model(history)

        validation = validate_invoice(data)

        if validation.ok:
            return ExtractionResult(data=data, status="ok")

        if validation.is_unrecoverable:
            # Info no está en la fuente → ruteo a humano
            return ExtractionResult(
                data=data,
                status="needs_human_review",
                reason=validation.reason,
            )

        # Recuperable: retry con feedback
        history.extend(_feedback_messages(data, validation.errors))

    return ExtractionResult(
        data=data,
        status="needs_human_review",
        reason="exhausted retries",
    )


def validate_invoice(data):
    errors = []
    unrecoverable = False

    # Reglas duras
    if data.get("stated_total") and data.get("calculated_total"):
        diff = abs(data["stated_total"] - data["calculated_total"])
        if diff > 0.01 and not data.get("discrepancy"):
            errors.append("stated and calculated totals differ but discrepancy=false")

    # Info no presente — no recuperable con retry
    if data.get("date_confidence") == "not_found":
        unrecoverable = True
        return ValidationResult(ok=False, errors=[], is_unrecoverable=True, reason="date_not_in_source")

    return ValidationResult(ok=not errors, errors=errors, is_unrecoverable=unrecoverable, reason=None)
```

## 🧪 Escenario de examen

**Pregunta tipo:** "Un sistema de extracción reintenta hasta 5 veces cuando el JSON no cumple el schema. Funciona bien para errores tipográficos, pero en ~3% de casos donde un campo NO está en el documento fuente, el sistema entra en bucle de retries y consume muchos tokens. ¿Mejor solución?"

**Opciones:**
- A) Aumentar `max_retries` a 10.
- B) **Permitir `null` en el schema para campos potencialmente ausentes, con un `*_confidence` o `*_status` indicando 'not_found', y rutear esos casos a revisión humana sin retry.**
- C) Bajar `max_retries` a 1.
- D) Subir el modelo.

**Respuesta:** **B**. La causa raíz es exigir info que no existe. Permitir "not_found" + ruteo a humano resuelve el bucle. **A** empeora el problema; **C** descarta retries útiles para errores genuinos.
