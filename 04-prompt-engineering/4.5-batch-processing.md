# 4.5 — Batch processing eficiente

> **Dominio 4 — Prompt Engineering & Structured Output · 20% del examen**

---

## 🎯 Concepto clave

La **Message Batches API** procesa lotes grandes con **50% de ahorro de coste**, ventana de hasta **24 horas**, y **sin SLA de latencia**. Es **asíncrona** — no apta para flujos en tiempo real. Cada item del batch es una **request independiente** (no soporta multi-turn tool calling en una sola request). El campo **`custom_id`** correlaciona request y respuesta porque el orden de resultados **no está garantizado**.

---

## 📚 Profundización

### Cuándo usar batches

🟢 **Apropiado:**
- Reportes/análisis **overnight**.
- Auditorías semanales de logs.
- Generación nocturna de tests.
- Evaluaciones masivas (cientos de outputs).
- Content moderation no en tiempo real.
- Backfill de embeddings/clasificación.

🔴 **Inapropiado:**
- **Pre-merge checks** (necesitas resultado en minutos).
- Chat en tiempo real.
- Cualquier flujo bloqueante de UX.
- Workflows con **multi-turn tool calling** dentro de la misma "conversación".

### Características clave (memorizar para el examen)

| Característica | Valor |
|---|---|
| Descuento sobre coste estándar | **50%** |
| Ventana máxima de procesamiento | **24 horas** |
| SLA de latencia | **Ninguno** |
| Orden de resultados | **No garantizado** |
| Correlación request ↔ resultado | Via **`custom_id`** |
| Formato de resultados | **JSONL** |
| Multi-turn tool calling en una request | **NO soportado** |
| Cada item del batch | Request **independiente** |

### Estructura de un batch request

```python
# Crear un batch
batch = client.messages.batches.create(
    requests=[
        {
            "custom_id": "doc-001",   # OBLIGATORIO
            "params": {
                "model": "claude-opus-4-5",
                "max_tokens": 1024,
                "messages": [{"role": "user", "content": doc1_text}],
            }
        },
        {
            "custom_id": "doc-002",
            "params": {
                "model": "claude-opus-4-5",
                "max_tokens": 1024,
                "messages": [{"role": "user", "content": doc2_text}],
            }
        },
        # ... hasta miles de requests
    ]
)

batch_id = batch.id
```

### Polling y descarga de resultados

```python
import time

while True:
    status = client.messages.batches.retrieve(batch_id)
    if status.processing_status == "ended":
        break
    time.sleep(60)  # poll cada minuto

# Descarga JSONL
results = client.messages.batches.results(batch_id)
for line in results:
    record = json.loads(line)
    custom_id = record["custom_id"]
    if record["result"]["type"] == "succeeded":
        message = record["result"]["message"]
        process(custom_id, message)
    else:
        log_error(custom_id, record["result"])
```

> Los resultados llegan **fuera de orden**. Sin `custom_id` no puedes correlacionar.

### Expiración

Si el batch no se procesa en 24h, **expira**. Hay que reintentarlo con un nuevo batch (no continúa).

### Cálculo de frecuencia de envío según SLA

> Caso del examen: tu SLA con el cliente es resultados en 30 horas. ¿Cómo enviar batches?

Razonamiento:
- Batch puede tardar hasta 24h.
- Por seguridad, ventanas de **4-6h** entre envíos para tener buffer.
- Submit cada 4h → en peor caso (acaba justo en 24h), resultado en 28h → cumple SLA de 30h.

```
SLA 30h, batch worst-case 24h → buffer = 6h
Frecuencia segura = SLA - worst_case = 6h
```

### Refinar prompts en sample antes de procesar volumen

> **Patrón obligatorio del examen.** Antes de enviar 10000 documentos a un batch, refinar el prompt en una **sample de 20-50**:

1. Procesa sample en API normal (sync, rápido feedback).
2. Audita outputs (humano).
3. Ajusta prompt y schema según los errores observados.
4. Repite hasta accuracy aceptable.
5. **Sólo entonces** lanza el batch grande.

Si lanzas 10000 directamente y el prompt es malo, gastas tokens y obtienes 10000 outputs malos. Coste **enorme**.

### Limitación: no multi-turn tool calling en una request

> Cada item del batch es **una llamada** a la Messages API. Si tu flujo es "modelo → tool → resultado → modelo → otra tool → ...", **eso no encaja en un batch item**.

Soluciones:
- Si la tarea es de un solo paso (clasificación, extracción): batch funciona.
- Si requiere agentic loop: NO uses batch. Usa la API síncrona y orquesta tú el loop.
- Si necesitas paralelizar agentic loops: lanza muchos workers, cada uno con su propio loop síncrono.

## ⚠️ Anti-patrones

### 🔴 Batch para workflows bloqueantes
Pre-merge check en CI con batch → el PR queda 24h sin merge. Usa API síncrona.

### 🔴 Lanzar batch grande sin refinar prompt
10000 outputs malos = mucho dinero perdido. Sample primero.

### 🔴 No usar `custom_id`
Sin correlación → no puedes mapear el resultado a tu input original cuando llegan fuera de orden.

### 🔴 Intentar agentic loop dentro de un batch item
No soportado. Tienes que orquestar fuera.

### 🔴 Asumir orden de resultados
El JSONL llega en orden arbitrario. Si tu pipeline asume orden, falla.

### 🔴 No manejar expiración
Si el batch expira, los items perdidos no se reintenta solos. Tienes que detectarlo y reenviar.

### 🔴 Polling agresivo
Sondear cada segundo no acelera el batch — sólo consume cuota. Cada 1-5 minutos basta.

### Pipeline completo: extracción nocturna de facturas

```python
def nightly_invoice_extraction(pdf_paths):
    # 1. Refinar en sample (UNA VEZ, durante desarrollo)
    sample = pdf_paths[:30]
    sample_results = [extract_sync(p) for p in sample]
    audit_human(sample_results)  # iterar prompt hasta accuracy OK

    # 2. Lanzar batch grande
    requests = [
        {
            "custom_id": f"invoice-{path.stem}",   # OBLIGATORIO
            "params": {
                "model": "claude-opus-4-5",
                "max_tokens": 2048,
                "tools": [INVOICE_TOOL],
                "tool_choice": {"type": "tool", "name": "record_invoice"},
                "messages": [{"role": "user", "content": load_pdf_text(path)}],
            }
        }
        for path in pdf_paths
    ]
    batch = client.messages.batches.create(requests=requests)

    # 3. Poll cada 5 min hasta listo
    while True:
        status = client.messages.batches.retrieve(batch.id)
        if status.processing_status == "ended":
            break
        if status.processing_status == "expired":
            handle_expired(status)
            return
        time.sleep(300)

    # 4. Descargar resultados y mapear por custom_id
    results_by_id = {}
    for line in client.messages.batches.results(batch.id):
        record = json.loads(line)
        results_by_id[record["custom_id"]] = record

    # 5. Procesar (con manejo de fallos parciales)
    for path in pdf_paths:
        rid = f"invoice-{path.stem}"
        if rid not in results_by_id:
            log_missing(rid)
            continue
        record = results_by_id[rid]
        if record["result"]["type"] != "succeeded":
            queue_retry(rid, record["result"])
            continue
        message = record["result"]["message"]
        store_extracted(path, message)
```

## 🧪 Escenario de examen

**Pregunta tipo:** "Un equipo necesita ejecutar Claude en cada PR antes de mergear como gate. Calculan que con batches ahorrarían 50%. ¿Mejor enfoque?"

**Opciones:**
- A) **NO usar batches: el pre-merge check requiere resultado en minutos. Usar la API síncrona normal aunque cueste 2x.**
- B) Usar batches con `custom_id = PR number` y polling agresivo.
- C) Lanzar un batch por PR (1 item).
- D) Combinar batch + un timeout de 10 minutos.

**Respuesta:** **A**. Batch tiene ventana de **hasta 24h sin SLA**: cualquier pre-merge gate quedaría bloqueado horas. Para workflows bloqueantes, el ahorro de 50% no compensa la latencia. **D** intenta combinar lo mejor de ambos pero batches simplemente **no garantizan** latencia.
