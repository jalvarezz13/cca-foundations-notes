# 4.6 — Arquitecturas de review multi-instancia y multi-pass

> **Dominio 4 — Prompt Engineering & Structured Output · 20% del examen**

---

## 🎯 Concepto clave

**Self-review (la misma instancia que generó el código lo revisa) detecta menos issues** que una instancia independiente: el modelo retiene su razonamiento y cuestiona menos sus propias decisiones. La práctica canónica es **una instancia genera, otra (sin contexto compartido) revisa**. Multi-pass añade dos niveles: **per-file** (detalle) + **cross-file integration** (visión global) → evita dilución de atención.

---

## 📚 Profundización

### Limitación documentada del self-review

> Cuando una instancia escribe código y luego se le pide revisarlo, **mantiene su modelo mental** de por qué tomó esas decisiones. Tiende a justificar más que a cuestionar.

Esto es **anchoring bias**. No es resoluble con prompting ("now be critical of yourself") — la mejor solución es **aislamiento de contexto**.

### Patrón "una genera, otra revisa"

```python
# Instancia A: genera
gen_messages = [{"role": "user", "content": "Implement function X..."}]
gen_response = client.messages.create(messages=gen_messages, ...)
generated_code = extract_code(gen_response)

# Instancia B: NUEVA conversación, revisa
review_messages = [
    {"role": "user", "content": f"Review this code for bugs, security, style:\n\n{generated_code}\n\nOutput JSON {{issues: [...]}}"}
]
review_response = client.messages.create(messages=review_messages, ...)
issues = extract_issues(review_response)
```

> La instancia B **no conoce** el prompt original ni el razonamiento de A. Es un revisor externo.

### Multi-pass: per-file + cross-file

> Dos niveles de granularidad, dos passes distintos.

```
PASS 1 — per-file (paralelo)
  Para cada archivo modificado:
    spawn(code-reviewer, prompt="Review file X for bugs/security/style")
  Output: lista de issues local

PASS 2 — cross-file integration (uno)
  spawn(integration-reviewer, prompt=
    "These files were modified together: [...]. Check for:
     - Broken interfaces between them.
     - Side effects (shared state mutations).
     - Inconsistent error handling across the chain.
     Do NOT repeat issues from per-file pass."
  )
  Output: lista de issues de integración
```

**Por qué funciona:**

- **Per-file**: cada archivo tiene un revisor dedicado → atención completa → detección detalle.
- **Cross-file**: un revisor con visión global → captura contratos rotos y side-effects.
- Combinados, cubren detalle e integración sin que ninguno se diluya.

### Anti-patrón: sólo whole-PR

```
spawn(reviewer, prompt="Review this PR with 30 files of changes")
```
→ **Dilución de atención**: el modelo prioriza algunos archivos, ignora otros. Pierde issues pequeños.

### Anti-patrón: sólo per-file

```
para cada archivo: spawn(reviewer, ...)
```
→ **Pierde integración**: cambios coherentes individualmente que rompen el conjunto.

### Verification pass con confidence

Patrón avanzado: después de detectar, **otra instancia verifica** los findings con confidence score:

```
PASS 1 — generación de findings (cobertura amplia, "report every issue")
PASS 2 — verification (cada finding: confidence high/medium/low)
PASS 3 — routing:
  high   → publicar
  medium → enviar a humano para sign-off
  low    → descartar o archivar para análisis
```

Cada pass es **instancia independiente** o al menos **conversación distinta** dentro de la misma sesión.

### Confidence calibrada

> Confidence score autoreportado por el modelo **no** está perfectamente calibrado por defecto. **Calibra con held-out set**:

1. Procesa 100-200 muestras con ground truth conocida.
2. Para cada `confidence` autoreportado, mide accuracy real.
3. Curva de calibración: si "high" significa 95% accuracy real → bien. Si significa 70% → overconfident.
4. Ajusta los thresholds del routing.

(Más detalle en Dominio 5.5.)

### Cuándo NO usar multi-pass

- Cambios triviales (un renombre, un literal): no compensa overhead.
- Diff muy pequeño (1-2 archivos): per-file + cross-file colapsan en uno.
- Latencia muy crítica (review en milisegundos): un solo pass.

### Costo vs beneficio

| Setup | Coste relativo | Issues detectados (típico) |
|---|---|---|
| Self-review | 1x | 60-70% |
| Una genera + otra revisa | 1.5x | 80-85% |
| Multi-pass per-file + cross-file | 2-3x | 90-95% |
| Multi-pass + verification | 3-4x | 95%+ con muy pocos FP |

→ Decide según el coste del fallo. Para infra crítica, 3x compensa.

## ⚠️ Anti-patrones

### 🔴 Self-review como única defensa
```python
response = generate_code(...)
review = same_client.messages.create(messages=[..., {"content": f"Now review: {code}"}])
```
Pérdida de ~25-35% de detección vs setup independiente.

### 🔴 Cross-file sin per-file
Pérdida de detalle. Issues locales pasan desapercibidos.

### 🔴 Per-file sin cross-file
Pérdida de integración. Contratos rotos pasan.

### 🔴 Whole-PR único
Dilución máxima. Sólo aceptable para PRs pequeños.

### 🔴 Asumir confidence calibrado sin medirlo
"high" puede ser 95% o 70%. Calibra con datos.

### 🔴 No deduplicar entre passes
Pass 1 reporta "missing await on line 42". Pass 2 también lo reporta. Confusión.

### 🔴 Confiar en self-reported confidence sin validación
Métricas en producción que no se calibran nunca → drift sin detectar.

## ✅ Patrón correcto

### Multi-pass review completo

```python
async def review_pr(changed_files: list[Path]) -> ReviewReport:
    # PASS 1 — per-file en paralelo (instancias independientes)
    per_file = await asyncio.gather(*[
        review_single_file(f) for f in changed_files
    ])

    # PASS 2 — cross-file integration (instancia NUEVA)
    integration = await review_integration(changed_files, exclude=per_file)

    # PASS 3 — verification con confidence (instancia NUEVA)
    verified = await verify_findings(per_file + integration)

    # Routing
    return ReviewReport(
        high_confidence=[f for f in verified if f.confidence == "high"],
        needs_human_signoff=[f for f in verified if f.confidence == "medium"],
        archived_low_confidence=[f for f in verified if f.confidence == "low"],
    )


async def review_single_file(path):
    # Instancia nueva, sin contexto compartido con la que generó el código
    return await client.messages.create(
        messages=[{"role": "user", "content": _per_file_prompt(path)}],
        tools=[REVIEW_TOOL],
        tool_choice={"type": "tool", "name": "report_issues"},
        ...
    )


async def review_integration(files, exclude):
    return await client.messages.create(
        messages=[{"role": "user", "content": _integration_prompt(files, exclude)}],
        tools=[REVIEW_TOOL],
        tool_choice={"type": "tool", "name": "report_issues"},
        ...
    )


async def verify_findings(findings):
    # Asigna confidence per-finding
    return await client.messages.create(
        messages=[{"role": "user", "content": _verify_prompt(findings)}],
        ...
    )
```

## 🧪 Escenario de examen

**Pregunta tipo:** "Un pipeline genera código con Claude y luego lo revisa con el mismo agente en la siguiente turnitud de la misma sesión. El equipo nota que el bot pasa por alto issues que un humano sí detecta. ¿Mejor solución?"

**Opciones:**
- A) Pedir al modelo "ser más crítico contigo mismo".
- B) **Hacer la review en una sesión nueva (instancia sin contexto compartido) o con otra instancia independiente. Ideal: combinar pass per-file en paralelo + pass cross-file de integración.**
- C) Subir el modelo.
- D) Reducir la temperatura.

**Respuesta:** **B**. El problema es anchoring (self-review). La solución estructural es **aislamiento de contexto**: la instancia que revisa **no ve** el razonamiento de la que generó. Multi-pass añade cobertura.
