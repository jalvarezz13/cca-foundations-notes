# 5.1 — Gestión de contexto en interacciones largas

> **Dominio 5 — Context Management & Reliability · ~15% del examen**

---

## 🎯 Concepto clave

En sesiones largas, dos enemigos: **(a) summarización progresiva** que condensa números, fechas y expectativas en frases vagas; y **(b) "lost in the middle"** — el modelo procesa mejor lo que está al **principio** y al **final** del input, peor lo del medio. La defensa canónica: **bloque persistente de "case facts"** repetido en cada prompt + **trim de tool outputs verbosos** antes de acumularlos + datos largos arriba, query al final + structura con XML.

---

## 📚 Profundización

### Riesgo de la summarización progresiva

Caso típico: una sesión de soporte que lleva 30 turnos. Si en cada turno el sistema "resume" la conversación previa para ahorrar tokens, **pierde información crítica**:

| Original (turno 5) | Tras 6 summarizations |
|---|---|
| "Order ORD-2024-3349, $487 USD, charged 2024-11-12, customer ID CUST-4892, refund partially attempted on 2024-12-01 ($150 refunded, $337 pending)." | "Customer wants a refund." |

→ Los **importes**, **fechas**, **IDs** y **estado** se han evaporado. El agente, sin esa info, alucina o pregunta de nuevo (frustración del usuario).

### Lost-in-the-middle

> Documento de Anthropic: el modelo procesa **mejor el principio y el final** del input. Información crítica enterrada en el medio tiene **menor probabilidad de uso**.

Implicaciones prácticas:

- **Datos largos arriba**, queries al **final**. Anthropic lo documenta como recomendación.
- Lo más importante: **principio Y final**. Resumen al inicio, query al final, datos importantes en ambos lados.
- Mientras menos esté "en el medio", mejor.

```
[ARRIBA — donde el modelo más atiende]
## Case facts (persistent)
- Customer: CUST-4892
- Order: ORD-2024-3349, $487 USD, 2024-11-12
- Identity verified: yes (2024-12-04)

## Conversation summary
- Customer reports double charge. Acknowledged. Investigating.

[MEDIO — donde menos atiende]
... historia completa de la conversación ...
... tool results acumulados ...

[ABAJO — donde vuelve a atender]
## Current question
The customer just asked: "Will I get the full $487 back or just $337?"
```

### Tool results inflan el contexto

> Una tool puede devolver 40+ campos cuando sólo 5 son relevantes. Acumulados, dominan el contexto.

Caso: `lookup_order` devuelve `{id, customer_id, customer_name, customer_email, customer_phone, shipping_address {…20 fields…}, billing_address {…20 fields…}, items: [...], total, currency, status, created_at, updated_at, paid_at, shipped_at, delivered_at, refund_history: [...]}`.

Si tu agente sólo necesita `{id, total, status, paid_at}`, el resto es **ruido caro**.

**Solución (PostToolUse hook):**

```python
async def post_tool_use(tool_name, tool_result, ctx):
    if tool_name == "lookup_order":
        trimmed = {
            "id": tool_result["id"],
            "total": tool_result["total"],
            "currency": tool_result["currency"],
            "status": tool_result["status"],
            "paid_at": tool_result["paid_at"],
        }
        return HookResult.replace(new_result=trimmed)
```

→ Menos tokens, menos ruido, mejor razonamiento.

### Bloque persistente de "case facts"

> Patrón canónico del examen: en **cada user message**, incluir un bloque con los hechos clave del caso (IDs, montos, fechas). Es **redundante** intencionalmente — garantiza que el modelo siempre los tenga frescos al principio Y al final.

```
## Case facts (always include in every turn)
- customer_id: CUST-4892
- order_id: ORD-2024-3349
- amount_cents: 48700
- currency: USD
- date_of_purchase: 2024-11-12
- identity_verified: true (since 2024-12-04)
- partial_refund_issued: 15000 cents on 2024-12-01
- pending_refund: 33700 cents

[resto del turno: pregunta o tool result]
```

### Structurar con XML headers

```xml
<case_facts>
  <customer_id>CUST-4892</customer_id>
  <order_id>ORD-2024-3349</order_id>
  ...
</case_facts>

<conversation_history>
  ... resumen breve ...
</conversation_history>

<current_question>
  The customer just asked: ...
</current_question>
```

> Tags XML ayudan al modelo a localizar bloques en el prompt.

### Técnicas oficiales de context engineering

Anthropic documenta tres técnicas operativas:

1. **Compaction**: resumir un bloque largo conservando hechos esenciales (no info accesoria).
2. **Tool-result clearing**: eliminar outputs verbosos de tools cuando el dato ya se ha extraído y se puede re-fetchear si se necesita.
3. **Memory**: persistencia externa estructurada (escribir hechos a un archivo o store y leerlo después).

Claude Code expone el comando `/compact` que aplica este patrón sobre la sesión actual.

### Devolver datos estructurados en vez de prosa

```
[asistente]
"He revisado el pedido. Llegó el 12 de noviembre y vale $487 USD. El cliente sí tiene
historial. Estoy investigando si se trata de un duplicado..."  ❌ disperso
```

vs

```
[asistente — bloque key facts]
{
  "investigation": "duplicate_charge_check",
  "order_id": "ORD-2024-3349",
  "amount_cents": 48700,
  "delivered_at": "2024-11-12",
  "customer_has_history": true
}

He revisado: pedido entregado el 12 de noviembre, $487 USD. Sigo verificando duplicado.  🟢
```

→ El bloque structurado es **fácil de incluir** en el siguiente turno como case facts. La prosa no.

## ⚠️ Anti-patrones

### 🔴 Summarización agresiva sin preservar hechos
Resúmenes que pierden números, fechas, IDs → el agente alucina.

### 🔴 Datos críticos en el medio del prompt
Si el case facts está enterrado entre conversación y tool results, lost-in-the-middle aplica.

### 🔴 No trim de tool outputs
`lookup_order` devuelve 40 campos en cada turno → contexto inflado en 30 turnos.

### 🔴 Confiar en que el modelo "recordará" el dato porque lo dijo hace 5 turnos
No. Repite los facts críticos en cada prompt.

### 🔴 Prosa vaga en lugar de datos estructurados
Difícil de reutilizar en el siguiente turno.

### 🔴 Ignorar `/compact` cuando la sesión es larga
Sesiones de 60+ turnos sin compactar → context window exhausted → el agente empieza a olvidar.

## ✅ Patrón correcto

### Estructura de prompt en sesión larga de soporte

```python
def build_turn_prompt(case_facts, recent_history, tool_results, user_message):
    return f"""
<case_facts>
{format_facts(case_facts)}
</case_facts>

<conversation_summary>
{summarize_briefly(recent_history)}
</conversation_summary>

<recent_tool_results>
{format_trimmed(tool_results, max_kb=10)}
</recent_tool_results>

<current_user_message>
{user_message}
</current_user_message>

INSTRUCTIONS: Use the case_facts above as ground truth (always cite specific IDs/amounts). If a tool result contradicts case_facts, raise the discrepancy explicitly.
"""
```

### Hook que trimea tool outputs verbosos

```python
RELEVANT_FIELDS = {
    "lookup_order": ["id", "total", "currency", "status", "paid_at", "items"],
    "lookup_customer": ["id", "email", "tier", "lifetime_value"],
}

async def post_tool_use(tool_name, result, ctx):
    fields = RELEVANT_FIELDS.get(tool_name)
    if fields:
        trimmed = {k: v for k, v in result.items() if k in fields}
        return HookResult.replace(new_result=trimmed)
    # Si no está en la whitelist, considerar trim genérico
    if size_kb(result) > 20:
        return HookResult.replace(new_result=summarize_for_model(result))
    return HookResult.passthrough()
```

## 🧪 Escenario de examen

**Pregunta tipo:** "Un agente de soporte falla tras ~25 turnos en una sesión larga: olvida montos, mezcla fechas, refiere a 'el pedido' sin especificar cuál. ¿Mejor solución?"

**Opciones:**
- A) Subir el modelo a uno con más context window.
- B) **Incluir un bloque persistente de 'case facts' (IDs, montos, fechas) en cada prompt + trim de tool results verbosos via PostToolUse hook + /compact periódico.**
- C) Cortar la sesión cada 10 turnos y empezar nueva.
- D) Pedir al modelo "recuerda todos los detalles".

**Respuesta:** **B**. Es la solución estructural: combina persistencia de facts (contra summarization loss), trim (contra inflación), y compactación (contra context exhaustion). **A** retrasa el problema pero no lo resuelve; **C** pierde continuidad; **D** ineficaz.
