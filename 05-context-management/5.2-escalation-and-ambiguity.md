# 5.2 — Escalado y resolución de ambigüedad

> **Dominio 5 — Context Management & Reliability · ~15% del examen**

---

## 🎯 Concepto clave

Hay tres triggers **válidos** de escalado: (1) **petición explícita** de humano por el usuario — honrar inmediatamente, sin "déjame intentar primero"; (2) **gap/excepción de política** — la regla es ambigua o silente sobre este caso; (3) **incapacidad de avanzar** — datos insuficientes irreparables. **Sentiment y confidence autoreportados NO son proxies fiables** de cuándo escalar — el modelo es mal juez de sí mismo. Para ambigüedad por datos múltiples, **pedir identificadores adicionales**, no usar heurísticas para "adivinar".

---

## 📚 Profundización

### Los 3 triggers válidos de escalado

| Trigger | Ejemplo | Acción |
|---|---|---|
| **Petición explícita** | "Quiero hablar con una persona." | Escalar de inmediato. Sin "déjame intentar primero". |
| **Gap de política** | El cliente pide un reembolso parcial 13 meses después de la compra; la política habla de 12 meses estrictos pero no del caso "13 meses con producto defectuoso". | Escalar con descripción del gap. |
| **Incapacidad de avanzar** | El sistema KB está caído; sin él, el agente no puede verificar elegibilidad. | Escalar con razón. |

### Triggers **NO** válidos (red flags del examen)

- 🔴 "El cliente parece frustrado" (sentiment).
- 🔴 "Mi confidence es baja" (self-reported).
- 🔴 "Es un caso complejo" (subjetivo).
- 🔴 "Hay muchas opciones" (debería pedir clarificación, no escalar).

### Honrar la petición explícita sin investigar primero

> Patrón canónico del examen: si el usuario dice "quiero hablar con un humano", **escalar de inmediato**. NO "permíteme intentar resolver esto primero".

Razón: el cliente ya ha decidido. Intentar resolverlo retrasa, gana frustración, y al final igual escala.

🔴 Mal:
```
Customer: "I want to speak to a human, please."
Agent: "I'd be happy to help! Let me first try to resolve this for you. What's the issue?"
```

🟢 Bien:
```
Customer: "I want to speak to a human, please."
Agent: "Of course. Let me hand you off to a specialist now. I'll include the context of our conversation so they can pick up where we left off." [escalate_to_human(transcript_id=...)]
```

### Reconocer frustración + ofrecer resolver, escalar si insisten

Sentiment **no** dispara escalado por sí solo, pero el agente debe **reconocer y ofrecer**:

```
Customer: "WHERE IS MY ORDER??? I'M SO TIRED OF THIS!"
Agent: "I hear how frustrating this is. Let me check your order right now."
[lookup_order(...)]
Agent: "I see your order shipped on Nov 5 but stuck in customs. I can either:
  1. Expedite a replacement (no charge).
  2. Issue full refund now.
  3. Connect you with a senior specialist.
What works best?"
```

Si tras la oferta el cliente insiste en humano → escalar.

### Sentiment y confidence autoreportados ≠ proxies de complejidad

> El modelo no es buen juez de sí mismo. Su "confidence" no se correlaciona bien con accuracy real (hace falta calibración explícita — ver Dominio 5.5).

Implicación: **no diseñes rutas que escalan automáticamente cuando `confidence < 0.7`**. El sesgo del modelo en confidence no garantiza que esos casos sean los que más necesitan humano. Mejor: rutar basándose en **señales objetivas** (categoría del problema, monto, tipo de cliente, edad del caso).

### Múltiples matches → pedir identificador, no adivinar

```
Customer: "I need help with my order."
Agent (busca): tiene 4 órdenes abiertas.

🔴 MAL: heurística que adivina la más reciente o la de mayor importe.
🟢 BIEN: "Tienes 4 órdenes activas:
  - ORD-2024-3349 ($487, Nov 12)
  - ORD-2024-3201 ($120, Oct 28)
  - ORD-2024-3150 ($890, Oct 20)
  - ORD-2024-3001 ($45, Oct 10)
¿Sobre cuál es tu pregunta?"
```

→ Pedir clarificación es **distinto** a escalar. No es escalado.

### Escalar cuando la política es silente o ambigua

```
Customer: "I bought 13 months ago. Product just broke. Warranty was 12 months but
the device clearly has a manufacturing defect (recalled batch)."

Policy: "Returns accepted within 12 months."
Policy: silent on "defective beyond warranty / recalled batch".

→ Escalar con: 
  - case_facts
  - reason: "policy_gap"
  - context: "Recalled batch number BAT-X12 confirmed; warranty expired by 30 days."
  - recommended_action: "approve_exceptional_replacement"
```

## ⚠️ Anti-patrones

### 🔴 Investigar antes de honrar petición explícita
"Let me try first" cuando el cliente ya pidió humano → frustración.

### 🔴 Escalar por sentiment
Cliente molesto no = caso complejo. Atiéndelo, ofrece resolver, escala si insiste.

### 🔴 Escalar por confidence autoreportado
No está calibrado. Métricas objetivas mejor.

### 🔴 Heurísticas para "adivinar" en ambigüedad
"Probably the most recent order" → riesgo de tocar el caso incorrecto.

### 🔴 Escalar sin payload estructurado
Pierde contexto → el humano tiene que volver a preguntar todo.

### 🔴 No reconocer la frustración antes de actuar
"I'll check your order" sin acknowledgment → el cliente se siente ignorado.

### 🔴 Esperar a que el caso falle para escalar gap de política
Detectar la silencia de la política **proactivamente** y escalar.

## ✅ Patrón correcto

### Decisión de escalado en código

```python
def should_escalate(case, ctx) -> EscalationDecision:
    # 1) Petición explícita — siempre primero
    if ctx.user_explicitly_requested_human:
        return EscalationDecision(
            yes=True,
            reason="explicit_user_request",
            urgency="immediate",
        )

    # 2) Incapacidad de avanzar
    if ctx.required_tools_unavailable:
        return EscalationDecision(
            yes=True,
            reason="cannot_proceed",
            context={"unavailable_tools": ctx.required_tools_unavailable},
        )

    # 3) Gap de política
    policy_match = ctx.policy.evaluate(case)
    if policy_match == "silent" or policy_match == "ambiguous":
        return EscalationDecision(
            yes=True,
            reason="policy_gap",
            context={"policy_evaluation": policy_match, "case": case},
        )

    # Sentiment / confidence NO se usan aquí
    return EscalationDecision(yes=False)
```

### Handoff con payload completo

```python
def execute_handoff(case, ctx, decision):
    payload = {
        "case_id": case.id,
        "customer_id": case.customer_id,
        "category": case.category,
        "root_cause": decision.reason,
        "facts": dataclasses.asdict(case.facts),
        "agent_actions_taken": ctx.actions_log,
        "policy_evaluation": decision.context.get("policy_evaluation"),
        "recommended_action": classify_recommendation(case, decision),
        "transcript_snippet": ctx.transcript[-5:],  # últimos 5 turnos
        "sla_remaining_minutes": (ctx.sla_deadline - now()).total_seconds() / 60,
    }
    handoff_queue.enqueue(payload, priority=ctx.case_priority)
```

## 🧪 Escenario de examen

**Pregunta tipo:** "Un cliente escribe: 'Estoy harto. Quiero hablar con una persona AHORA.' El agente está configurado para escalar cuando el sentiment es 'negative' y confidence < 0.7. ¿Mejor diseño?"

**Opciones:**
- A) Mantener la lógica actual.
- B) **Honrar la petición explícita inmediatamente, sin investigar antes ni evaluar sentiment/confidence. Escalar con payload estructurado al instante.**
- C) Cambiar el threshold de confidence a 0.5 para escalar más rápido.
- D) Añadir un paso "let me try to help first" antes de escalar.

**Respuesta:** **B**. Petición explícita es trigger inmediato. Sentiment/confidence son señales no fiables. **D** es el anti-patrón clásico que frustra al cliente.
